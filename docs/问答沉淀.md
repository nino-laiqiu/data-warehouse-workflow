# 问答沉淀

**分析师怎么问、怎么追问、在哪里反驳我们——这是全系统最贵的数据。** 它比任何需求文档都真实：需求文档写的是"他们说要什么"，问答记录写的是"他们实际卡在哪"。

## 为什么是这批数据

| 信号 | 说明什么 | 变成什么 |
|---|---|---|
| 同一个问题被 3 个人问过 | wiki 里没有，或写在没人找得到的地方 | 取数路径 / 常见问法 |
| 追问"那 XX 呢" | 上一版回答少了一个维度 | 口径页补边界 |
| "不对，应该是……" | 我们给错了，或口径有歧义 | 04_踩坑（最高价值） |
| "XX 是什么"而库里没有 | 术语缺口 | 术语页 / 本体 |
| 同一组表反复一起查 | 缺一条成型的取数路径 | join 说明 |

注意最后一条的**反面**：没人问的问题不值得写。知识库的 KPI 不是页数，是"同类追问下降"。

## 数据长什么样

一条记录 = 一轮问答，契约 [`contracts/qa_record.schema.json`](../contracts/qa_record.schema.json)：

```json
{
  "qa_id": "Q20261127-0001",
  "ts": "2026-11-27T09:12:04+08:00",
  "session_id": "s-20261127-a",
  "turn_no": 1,
  "question": "近30天各渠道GMV是多少",
  "answer": "按 pay_time 归日、不含运费、退款不回冲……",
  "sql_text": "SELECT ...",
  "tables": ["dwd_pay_flow_di", "dim_channel_df"],
  "feedback": 1
}
```

三个字段是这套东西的命门：

- `session_id` + `turn_no`：**没有会话，就没有追问**。单条问答只能看出"问了什么"，看不出"哪里没讲清"。
- `sql_text` + `sql_hash`：SQL 是口径的落地形态，指纹用于统计"同一条 SQL 被复用了几次"。
- `feedback`：1 有用 / -1 无用 / 0 未评。**只统计有反馈的，别把沉默当满意。**

## 存在哪

| 环境 | 位置 | 说明 |
|---|---|---|
| 生产 | MySQL `dw_qa`（[db/schema_mysql.sql](../db/schema_mysql.sql)） | 三张表：`qa_session` / `qa_turn` / `qa_candidate`，utf8mb4 |
| 本地 | `.data/qa.db`（SQLite，不入库） | 字段与 MySQL 一致，跑通同一条链路；`export-sql` 可整库灌进 MySQL |
| 交换格式 | JSONL（`data/qa/*.jsonl`） | 约定用，方便从任意系统导出 |

换存储只改 `tools/qa_store.py` 的 `connect()`，其余代码不动——这是"换载体不改代码"的最小实现。

## 四道工序

```
① 采集  分析师问答 → JSONL/直连 → qa_store.py ingest
② 挖掘  qa_mine.py：四个机械信号 → 候选知识（不改任何现有文件）
③ 裁决  人看 candidates.md：转正 / 驳回（qa_promote.py）
④ 登记  wiki_impact.py --stamp --note "为什么" → index.md 留痕
```

**②不许直接写知识库。** 挖出来的是"值得看一眼的东西"，不是结论——自动写进 wiki 等于让模型自己给自己判卷。

## 命令

```bash
python tools/qa_store.py init
python tools/qa_store.py ingest --file data/qa/sample.jsonl
python tools/qa_store.py stats                    # 会话/轮次/反馈/高频表组合
python tools/qa_mine.py --week 2026-W48           # → 知识候选/2026-W48/candidates.md
python tools/qa_promote.py --list
python tools/qa_promote.py --id C-20261128-01 --kind knowledge \
    --dir 04_踩坑 --slug aov-vs-arpu --title "客单价 AOV 与人均消费额 ARPU 不是一回事" \
    --conclusion "AOV=GMV/订单数；ARPU=GMV/支付人数，分母不同不能互替"
python tools/wiki_impact.py --stamp --note "新增：AOV 与 ARPU 的区分"
```

`--kind ontology` 走另一条路：只生成 ontology_delta **提案**，本体仍然只能人改（有意的减速带）。

## 红线

1. **不存真名与手机号**。`user_hash` 只存哈希；问题文本里如果出现手机号、身份证号，采集侧就要打码。
2. **只追加，不修改**。同一 `qa_id` 内容变了就拒绝入库——问答记录是证据，改了就不是证据了。
3. **候选知识必须人审**。`qa_promote.py` 只搬证据、对齐格式，不替你下结论。
4. **反馈别看均值**。有用的回答和没用的回答混在一起算平均，什么都看不出来。

## 现状与缺口

- ✅ 契约、SQLite 镜像、MySQL DDL、导出、四个挖掘器、转正、登记，已跑通（示例 7 轮问答 → 4 条候选 → 转正 1 条进 `knowledge/04_踩坑/`）
- ⬜ 还没有真正的采集入口：现在是手动 `ingest --file`，接线上要在 A 线（取数对话）结束时落一条
- ⬜ 巡检还没统计"候选积压"——待审候选堆积是最容易烂掉的地方
- ⬜ 没有做 PII 打码工具，目前靠采集侧自觉
