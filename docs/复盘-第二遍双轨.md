# 复盘：第二遍双轨（渠道 GMV 日报，subagent 真跑）

> 时间：2026-11-28　需求：REQ-20261122-01　执行方式：developer-1 / developer-2 各由一个 subagent 独立并行实现，监督者再做第三轮比对裁决。
> 目的：验证三件事——**双轨隔离是不是真的**、**门禁在陌生需求上还灵不灵**、**"手工也能过门"的怀疑是真是假**。

## 一、结论先说

| 问题 | 结论 | 证据 |
|---|---|---|
| 双轨隔离是真的吗 | **产物层面是真的**，但**过程无法被证明** | 两轨 SQL 无相同文件、行级相似度 0.364 / 0.39；监督者从中裁出 8 条实质差异（结构 1 / 实现 7） |
| 门禁在陌生需求上灵吗 | **形式门禁灵，语义门禁基本是空的** | G0/G1/G2 都过了；但把 `COUNT(DISTINCT order_id)` 改成 `COUNT(1)` 没有任何门禁能发现 |
| 手工能过门吗 | **不是"能糊弄"，是"机器没查"** | sk-sql-ddl 只认 `CREATE TABLE`，DML 无校验器（sk-sql-dml 只有规格），sk-sql-guard 同样只有规格 |

真正抓出问题的是**角色**，不是门禁：监督者发现 B 轨维表未聚合会扇出（S1），两个开发者各自独立发现 `channel_code` vs `channel_id` 冲突、`pay_status` 枚举未登记、`other` 不在 CHANNEL 字典。

## 二、两轨到底差在哪（8 条，节选）

| # | 层面 | A 轨 | B 轨 | 裁决 |
|---|---|---|---|---|
| S1 | 结构 | 维表先 `GROUP BY + MAX` 再 JOIN | 直接 JOIN 维表 | a（B 会扇出，破坏"同 dt+渠道一行"） |
| D1 | 实现 | 缺失渠道归 `other` | 归 `unknown` | a（wiki 03:125 有 `other` 惯例） |
| D3 | 实现 | 只 `COALESCE`，空串漏网 | `COALESCE(NULLIF(TRIM(...),''),...)` | merge（取 B 的归一化 + A 的 `other`） |
| D4 | 实现 | 去重键 `(order_id, pay_seq)` | 退化为 `COALESCE(pay_seq, pay_id)` | a（知识库主键不含 pay_id，退化未经证实） |
| D6 | 实现 | 只靠 `dt='${dt}'` | 额外 `TO_DATE(pay_time)=TO_DATE('${dt}')` | a（dt 错标时会多丢行） |
| D7 | 实现 | AOV `DECIMAL(18,2)` | `DECIMAL(18,4)` | b（精度更高，不动口径） |

这批差异正是双轨要买的东西：**它们不是"谁写错了"，而是"哪种选择更站得住"**。单轨只会产出其中一种，且没人会去论证它。

## 三、需要完善的地方（按优先级）

### P0 语义门禁缺位
- **DML 完全没有校验器**。`sk-sql-ddl/validate.py --sql <ETL>` 直接报"必须以 CREATE TABLE 开头"——它对 DML 是拒收，不是校验。
- 后果：P2/P5 最贵的产物（ETL）只有人工 review 这一道。
- 建议：实现 `sk-sql-dml`（sqlglot AST：只读上游表白名单、必须有静态分区 OVERWRITE、禁 `SELECT *`、聚合里 `COUNT(DISTINCT ...)` 与 `SUM` 的关系可提示），并把 `sk-sql-guard` 的六条规则代码化（chat.py 里已有现成实现可抽取）。

### P1 G2-3 是空条款
- `journal 中无跨轨读取事件` 依赖"谁读了哪个路径"的记录，而系统**没有任何读取审计**，G2 只记 pass 也不会有人发现。
- 现在 `tools/check_dual_track.py` 只能查产物里的跨轨标识（间接物证），且会误报（"未读 developer-2" 这种自证句要按否定语境排除，已处理）。
- 建议：subagent 派活时把「必读清单 + 禁读清单」写进 `prompts/<role>.md`（已有），并在 journal 里记一条 `conversation` 存该 prompt 的 sha256——至少能证明"派活时怎么说的"。真正的读取审计要等运行时支持。

### P2 G1 可以被历史稿绕过
- 本次 G1 报 `[WARN] 没有审阅状态文件（历史稿，按已确认处理）`，即需求分析员的对话式翻译流程**可以整个跳过**还过门。
- 建议：对新建需求（登记日期 ≥ 2026-11-28）把这条 WARN 升级为 FAIL；历史稿保留白名单。

### P3 产物布局漂移
- 画像标签那次两轨把 SQL 直接放在轨道根目录，这次放在 `sql/`。`roles.json` 写的是 `sql/*.sql`，但没人管。
- 已让 `check_dual_track.py` 报 WARN。建议加一条硬规则：轨道根目录出现 `*.sql` 即 FAIL（约定就是 `sql/`）。

### P4 巡检把"没跑过门禁"和"门禁没过"混为一谈
- 巡检只认 journal 里的 gate 事件。我实际跑了 G0/G1 且都 PASS，但没记事件，报告就说"未过门"——**门禁结果靠人记得去记，就会漏**。
- 建议：让每个门禁脚本在成功时自己写 gate 事件（或由 `inspect.py` 直接调校验器判定，而不是读 journal）。当前是后者只有"需求登记 G0"一项做了。

### P5 角色提示词会过期
- `roles.json` 里输入路径写的是 `REQ-*-translation.md`、且 developer-1 的输入含 `监督者/final/*.sql`（P2 阶段根本不存在）。生成出来的提示词把开发者指向不存在的文件。
- 已修：`REQ-*.md`，并把 final 从 P2 输入里拿掉（P5 才读）。

### P6 契约校验命令反直觉
- `validate_contracts.py <data.json> [--schema X]`，第一个位置参数是**数据**不是 schema。监督者按常见直觉传了 schema 在前，直接报"找不到对应 schema"。
- 已在 `flow/gates.yaml` 的 G3 里写全命令；建议工具对"第一个参数是 .schema.json"直接给出纠错提示。
