# 全局规范

全仓唯一的"约法"。它不解释为什么（那在 `memory/decisions/`），只规定**做什么、不做什么**。违反的项尽量都有脚本拦；拦不住的靠评审。

## 1. 口径只在本体

- 口径（指标怎么算、字段什么意思、枚举有哪些值）**只能**写在 `ontology/`。
- 任何角色都不得直接改 `ontology/`——只有人能改。提案走 `contracts/ontology_delta.schema.json`。
- 知识的写法：`knowledge/` 写"怎么写、踩过什么坑"，**不写口径**。发现口径类内容，转成 delta 提案。

## 2. 一个需求一个顶层目录

```
requirements/<短名>需求<YYYYMMDD>/
├── 反馈者/            原件，只增不改（证据）
├── 需求分析员/        翻译稿（合同）
└── 需求开发员/        developer-1 / developer-2 / 监督者 / 质量 / 血缘 / 交付 / journal.jsonl
```

- 需求目录名必须 `<名字>需求<YYYYMMDD>`，日期与 `REQ-YYYYMMDD-NN` 编号一致。
- 不许把需求文件平铺在 `requirements/` 下。
- 全局登记簿 `requirements/_registry.jsonl` 只由 `sk-req-register` 追加。

## 3. 交接只能是机器可读契约

- stage 之间只传 `contracts/*.schema.json` 定义的结构，**禁止自然语言交接**（"按天聚合"这类话会在下游变成两种分区写法）。
- 缺字段 = 硬失败，不做"合理推断"。
- **顺序只认 `flow/pipeline.yaml` 的 `depends_on`**：每 stage 必须显式声明（可为 `[]`），这是"谁必须等谁"的唯一权威——文档段落顺序机器读不出来。只有声明了 `parallel_tracks` 的 stage 允许并行（当前只有 P2 的两个开发者）；监督者所在 stage 不得并行，且必须依赖 P2。
- 改 pipeline 后跑 `python tools/check_pipeline.py`；派活前由 `tools/chat.py task` 复核，缺件直接拒绝。

## 4. 留痕只追加

- `journal.jsonl` 六类事件：`conversation` / `query` / `artifact` / `progress` / `todo` / `gate`，口径见 [`docs/追踪.md`](追踪.md)。
- 历史条目永不修改；写错就追加一条带 `supersedes` 的更正。
- 谁生成产物谁记账，不许"事后补一份漂亮的 journal"。

## 5. 知识库：新增直接加，改老口径要登记

- 新增页 / 新增小节 → 直接加。
- 改已有页（口径、公式、字段含义、结论）→ 必跑 `tools/wiki_impact.py --changed` 看影响面，再 `--stamp --note "变了什么"` 写进 `knowledge/index.md`。未登记由 `--check` 拦。

## 6. 命名

- 表名：`<层>_<域>_<主体>_<粒度>`，层 = ods/dwd/dws/ads/dim，粒度 = di（日增量）/ df（日全量）/ 1d（日汇总）。
- 字段后缀：`_amt` 金额、`_cnt` 计数、`_qty` 数量、`_rate` 比率、`_dur` 时长；`is_` 布尔、`dt` 日期分区。
- 比率列一律 `_rate` 且是 0–1 小数，不存百分数。

## 7. 时间

- 分区值 `dt` 一律 `YYYY-MM-DD` 字符串。
- 窗口统计写 `[dt-N, dt-1]`，**不含当天**（当天数据不全，含进去每天都会变）。
- 涉及跨时区的事件时间必须显式声明时区。

## 8. SQL

- 只允许单条语句；禁 `DROP` / `TRUNCATE` / `ALTER` 混在交付脚本里。
- `SELECT *` 一律禁止；JOIN 不超过 3 个（更多就该先落中间表）。
- 建表必须每列有 `COMMENT`、必须有 `STORED AS`、分区列不得同时出现在列定义里。
- A 线（取数）只读：`SELECT`/`WITH`，必须带 `dt` 过滤且窗口 ≤ 90 天，`LIMIT 2000`。

## 9. 提交

- 一律走 API 通道：`& .\tools\push.ps1 -Message "..." -All`（原理见 [`docs/推送流程.md`](推送流程.md)）。**不用 `git push` 直连**——本机 TLS 与凭据提示都会挂。
- 中文提交信息写文件再提交，别塞进命令行（会被按空格切碎）。
- 不 `force push`，不改写已推送历史。

## 10. 校验

- 改完必须跑：`python tools/inspect.py`（全量）+ 你改动直接相关的那个校验器。
- 校验器退出码非 0 就是失败，不许"看着像过了"。
- 所有工具**只用标准库**（本机没有 PyYAML / jsonschema），单命令零依赖。

## 11. 人工卡点只有 3 个

| 卡点 | 位置 | 人在决定什么 |
|---|---|---|
| H1 口径确认 | P1 翻译完成 | 这个口径对不对 |
| H2 方案裁决评审 | P3 比对完成 | 选 A 还是合，理由成立吗 |
| H3 上线放行 | P5 血缘调度后 | 能不能上生产 |

任何人不得增加卡点，也不得绕开这 3 个。豁免要落 `memory/rulings/`。

## 12. 角色编制固定 5 个

需求分析员、开发者 1、开发者 2、监督者、追踪者。加角色要先改 [`memory/decisions/ADR-0003-five-agents.md`](../memory/decisions/ADR-0003-five-agents.md)，`tools/check_agents.py` 把"必须是 5 个"写成了硬检查。

## 13. 问答沉淀：只追加，候选必须人审

- 每条问答记 `qa_id`/`session_id`/`turn_no`；同一 `qa_id` 内容变了**拒绝入库**，问答是证据，改了就不是证据。
- 不存真名与手机号，只存 `user_hash`。
- 挖掘出来的候选**不能直接进 `knowledge/`**：走 `qa_promote.py` → 人填结论 → `wiki_impact.py --stamp` 登记。
- 候选驳回要显式 `--reject`，别让它自然沉底——沉底的候选三个月后会原样再被问一遍。
- `.data/`（本地问答镜像）不入库；跨环境交换用 JSONL 或 `export-sql`。

## 反例（看到就该改）

- 把临时脚本丢在仓库根目录；
- 在 `knowledge/` 里写指标公式（那是本体的事）；
- 用 `AVG(日客单价)` 算月客单价（应该 `SUM(GMV)/SUM(订单数)`）；
- 改了知识页但没在 `knowledge/index.md` 留一行；
- 门禁没过就先干下一步，然后补一条"已通过"。
