# 核心能力与自动化设计（v0.3）

> 定位：**围绕数仓开发的多智能体协作 + 知识库驱动 + 全过程留痕**。
> 这份文档把七个核心能力拆成可判定的条款，并标出当前仓库的缺口。设计文档（v0.2）讲的是流程长什么样，这份讲的是流程靠什么自动转起来。

## 一句话

不是"用 LLM 写 SQL"，是"让一次数仓开发变成一条可复现、可审计、越跑越省力的流水线"。

## 七个核心能力

每条按五格写：**定义 / 判据（怎么算做到了）/ 触发 / 落盘在哪 / 现状**。

### C1 多智能体协作

- **定义**：角色单一职责、输入输出可判、彼此不越权；编排器只派活与验门，不写产物。
- **判据**：每个角色有独立定义文件；任意一次运行，产物都能指到"哪个角色在哪个阶段产出"；无角色跨权写文件（如开发者改本体）。
- **触发**：需求进入 P0。
- **落盘**：`agents/*.md`、`flow/pipeline.yaml`、`journal.jsonl` 的 `actor` 字段。
- **现状**：11 个角色只有 5 个有独立文件（orchestrator / requirement-translator / chronicler / developer / supervisor），其余 6 个只有 `agents/README.md` 里的一行矩阵；编排器从未真正运行过（一直是人在对着文档执行）。

### C2 知识库驱动

- **定义**：产出必须能追溯到知识条目，而不是模型"记得"某种写法。知识库存"怎么写 / 踩过什么坑"，不存口径。
- **判据**：每条 SQL / 质量规则 / 血缘定义都能列出它引用的 chunk id；chunks 索引覆盖率 = 有索引的知识文件 ÷ 知识文件总数。
- **触发**：P2 开发、P4 规则、P5 血缘。
- **落盘**：`knowledge/**`、`knowledge/index/chunks.jsonl`。
- **现状**：16 个知识文件、8 条 chunk 索引（覆盖率 50%，导航页不计）；**改老口径的闭环已实现**——`tools/wiki_impact.py --changed` 算影响面（谁链接、谁引用），`--stamp --note` 更新 sha256 指纹并写 `knowledge/index.md` 的变更记录，`--check` 拦住"改了没登记"，已接进巡检；**但产出仍未强制引用 chunk**——契约里没有 `knowledge_refs` 字段（下一个缺口）。

### C3 需求自动化（= 需求雷达）

用户 m02077 的原话定义：**"能扫描原始需求文档 看是否有新增需求 有则提醒是否需要开发"**。

- **定义**：盯着原始需求文档的投放目录（`需求池/`），发现新增或改过的文档就提醒人"这个要不要开发"；人不确认，就不进流程。
- **判据**：同一份文档不会重复提醒（按 sha256 去重）；改过的文档会再提醒一次；提醒里带标题、路径、时间；人确认后能一条命令接到 P0 登记。
- **触发**：定时（每天一次即可）+ 人工随时手动跑。
- **落盘**：`需求池/_scan_state.json`（每个文件的 hash 与首见时间）、`需求池/_待确认.md`（给人看的勾选清单）。
- **现状**：✅ `tools/scan_requirements.py`，已测（首次报 2 新增、二次 0 新增、改文件报 1 变更）。

**边界**：这只是"发现"。把需求翻译成可开工规格是 P1 需求翻译者的事，不在 C3 里。之前把两件事混成一个"需求自动化"是我表述过头了。

### C4 全过程留痕

- **定义**：每个动作留事件，每个产物留哈希，每个门禁留理由；任何时点可回放到"当时为什么这么定"。
- **判据**：journal 里 artifact 事件的 hash 与实际文件一致；每个门禁事件能指到检查输出的具体行；不存在"改了文件但没留痕"的产物。
- **触发**：每次写文件、每次过门禁。
- **落盘**：`journal.jsonl`、`contracts/journal_entry.schema.json`、`memory/decisions/`。
- **现状**：journal 46 条（28 artifact / 11 conversation / 7 gate），artifact hash 靠 `.tmp/gen_journal.py` 手工补；**没有写文件的钩子**，所以"忘记录"一定发生。

### C5 记忆体系

- **定义**：三层分工——运行记忆（journal/runs，短期）、决策记忆（ADR/rulings，中期、只增不改）、长期知识（knowledge/wiki，可修订但有 verified_by）。
- **判据**：每条决策能追到一次运行；每个知识点有验证者；过期条目（>90 天未被引用且状态 draft）会被巡检点名。
- **触发**：决策发生时写 ADR；每次运行结束做一次"晋升判断"。
- **落盘**：`memory/{decisions,rulings,reviews,lessons}`、`knowledge/wiki/`。
- **现状**：ADR-0001/0002 有余，lessons/reviews/rulings 基本空白；**没有晋升规则的可执行版本**（什么条件下 journal 的教训能变成 lessons）。

### C6 数据开发规范

- **定义**：命名、分层、分区、注释、幂等、质量规则全部可机器检查，且检查器就是规范本身（文档与代码不许两套说法）。
- **判据**：DDL/DML 各有校验器；规范页里的每条硬规则对应一条可执行检查；违规能被拦在门禁而不是评审会上。
- **触发**：P2 产出、P5 上线。
- **落盘**：`ontology/schema/`（元模型）、`skills/sk-sql-*/`、`knowledge/wiki/01-命名与词根.md`。
- **现状**：DDL 有校验器（列名 / 分区重复 / COMMENT / STORED AS / 单语句）；**DML 还没有**（sk-sql-dml 待建）；`gmv` 之类口径只在本体，规范页不重复——这条边界守住了。

### C7 定时驱动（wiki 更新 / 记忆更新 / 每周巡检）

- **定义**：把"该周期性做的事"从人的记忆里挪到调度器里：每周刷新 wiki 一致性、做一次记忆晋升与去重、跑一次全仓巡检并出报告。
- **判据**：三类任务有明确的 cron 表达式与产物路径；巡检报告能回答"本周哪里退化了"；连续两次巡检可对比出趋势。
- **触发**：定时（周级）。
- **落盘**：`runs/inspection/<YYYY-Www>/{report.md,report.json}`、`memory/reviews/`。
- **现状**：**完全没有**。今天所有检查都要人手敲，这也正是"开了新窗口就失忆"的根因之一。

## 三条必须守住的边界

1. **口径只在 ontology**。知识和记忆都不许定义"GMV 怎么算"；它们只能写"怎么写更省资源 / 上次这么写踩了什么坑"。自动积累最容易污染的就是这条线。
2. **自动到"待签"，不自动到"签"**。H1/H2/H3 是人的责任，机器可以准备好材料、给出建议，但不能替人签字。真要放开，必须走 `memory/rulings/waivers.json` 留痕。
3. **留痕不可编辑**。journal 只追加；写错了就再写一条更正，不能改历史。

## 名词：ontology_delta（本体变更提案）

一句话：**它是"我想改口径"的申请单，不是改动本身。**

- **为什么要有**：口径只能有一个地方定义（`ontology/`），否则知识库和代码会各自长出一套"GMV"。但如果谁都不能改本体，业务一变流程就死。所以留一个**正规入口**：任何人都可以提"我想加/改/废一个本体条目"，但只有本体管理员能落。
- **谁提**：P1 需求翻译者（发现需求里的名词本体没有）、P2 开发者（发现建模需要的字段本体没有）、A 线分析（发现口径缺定义）。
- **长什么样**（`contracts/ontology_delta.schema.json`）：`requirement_id` + `proposer` + `reason`（为什么非改不可）+ `changes[]`；每条 change 写 `op`（add/update/deprecate/rename）、`kind`（object/process/metric/dict/link/constraint）、`target`、`why`，可选 `field`/`from`/`to`/`replacement`。另可带 `impact`（谁要跟着改）与 `migration`（怎么改、要不要重跑）。
- **为什么叫 delta**：只写"变了什么"，不复制整份本体——复制就会分叉，delta 不会。
- **走到哪**：提案 → 本体管理员评审（改得对不对、会不会破坏已有依赖）→ 落到 `ontology/` → journal 记一条 → 下游产物（DQ、SQL、文档）重新生成并 diff。没落的提案不许当口径用。
- **真实例子**：`requirements/画像标签需求20261122/需求开发员/本体变更/ontology_delta.json` —— 12 个标签有枚举/分档/数值三类值域，但 `TAG` 只有 `tag_code` 和 `category`，导致 DQ-003 只能把枚举硬编码进 SQL。补 `value_type` + `value_domain` 两条 add，`impact` 明确"13 列 + DQ-003/009 需重生成"。

**和"知识自动积累"的区别**：ontology_delta 改的是"是什么"（口径），必须人评审；知识自动积累写的是"怎么做、踩过什么坑"，可以机器自动写（见 X2）。

| # | 冲突 | 建议 |

## 巡检检查什么（M5 的口径）

分五组，全部只读、不改任何文件：

1. **门禁组**：跑现有 11 个校验器，逐项 PASS/FAIL，失败取首行原因。
2. **结构组**：目录是否符合"需求优先"、需求目录三角色是否齐、开发目录是否齐。
3. **闭环组**：每个需求走到哪个门（G0…G6）、缺哪一环、HITL 积压多久（如 G5 因 H3 未签已挂 N 天）。
4. **资产组**：本体状态分布、契约覆盖（有几份 schema / 设计要 9 份）、技能实现率、知识索引覆盖率。
5. **卫生组**：status: draft 超 90 天、孤儿目录、未留痕产物、空目录占位。

输出：`runs/inspection/<YYYY-Www>/report.md`（人看）+ `report.json`（下周对比用）。

## M6 设计提案：自动留痕（做成 skill，不做成智能体）

**结论先给：做成一个 skill（`sk-trace-record`），不做成智能体。** 理由是这件事没有判断、只有动作——算 hash、追加一行、校验格式；做成智能体等于让模型每次现编一遍 JSON，还会因为"这条不重要吧"漏记。

### 技能契约

输入（缺一不可，缺了就拒绝执行）：

| 字段 | 含义 | 例子 |
|---|---|---|
| `run_id` | 哪次运行 | `画像标签需求20261122` |
| `type` | 事件类型 | `artifact` / `gate` / `conversation` |
| `actor` | 谁干的 | `developer-2@1.0.0` |
| `path` | 产物路径（artifact 必填） | `.../需求开发员/监督者/final/03_etl.sql` |
| `reason` | 一句话说明 | `按 H2 裁决合并两条 CTE` |

行为：① 读该文件先算 `hash_after`，若文件不存在则报错（留痕不能凭空造）；② 从 journal 里取同一 path 的上一条 `hash_after` 作为 `hash_before`；③ 追加一行 `journal.jsonl`；④ 用 `contracts/journal_entry.schema.json` 自校验，不合法就不写。

三条硬规则（防止它变成橡皮章）：

1. **hash 没变、reason 又是空的 → 不记**。产物没动就没有事件，否则 journal 会被"我确认了一下"刷满。
2. **同一个 path 连写两条，第二条必须说明为什么**（`reason` 非空），否则拒绝。
3. **只追加**：无 `--force`、无覆盖、无删除。写错了再写一条 `type: conversation` 的更正。

### 它解决什么

现在"谁生成产物谁记账"是**靠人自觉**（X4 的退让方案），M4 那轮就是活干完了、journal 后补的。有了 skill，生成器只要在写盘后调一次，留痕从"记得做"变成"顺手做"。

### 智能体在哪用

只在**判断**上用：周巡检里跑一个"这周哪些变更值得晋升成 lesson"的 agent，读 journal 片段 → 产出候选清单 → 人勾选。写 journal 本身绝不让模型自由发挥。

### 检查项

巡检加一条"未留痕产物 = 0"：遍历 `需求开发员/` 下所有 `.sql`/`.json`/`.md`，凡是没有对应 artifact 条目的，列出来——这就是 M6 的验收判据。
