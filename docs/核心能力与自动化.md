# 核心能力与自动化设计（v0.3）

> 定位：**围绕数仓开发的多智能体协作 + 知识库驱动 + 全过程留痕**。
> 这份文档把七个核心能力拆成可判定的条款，并标出当前仓库的缺口。设计文档（v0.2）讲的是流程长什么样，这份讲的是流程靠什么自动转起来。

## 一句话

不是"用 LLM 写 SQL"，是"让一次数仓开发变成一条可复现、可审计、越跑越省力的流水线"。

## 七个核心能力

每条按五格写：**定义 / 判据（怎么算做到了）/ 触发 / 落盘在哪 / 现状**。

### C1 多智能体协作

- **定义**：角色单一职责、输入输出可判、彼此不越权；编排器只派活与验门，不写产物。
- **判据**：每个角色有独立定义文件；任意一次运行，产物都能指到"哪个角色在哪个阶段产出"；无角色跨权写文件（如开发者改本体）。
- **触发**：需求进入 P0。
- **落盘**：`agents/*.md`、`flow/pipeline.yaml`、`journal.jsonl` 的 `actor` 字段。
- **现状**：11 个角色只有 5 个有独立文件（orchestrator / requirement-translator / chronicler / developer / supervisor），其余 6 个只有 `agents/README.md` 里的一行矩阵；编排器从未真正运行过（一直是人在对着文档执行）。

### C2 知识库驱动

- **定义**：产出必须能追溯到知识条目，而不是模型"记得"某种写法。知识库存"怎么写 / 踩过什么坑"，不存口径。
- **判据**：每条 SQL / 质量规则 / 血缘定义都能列出它引用的 chunk id；chunks 索引覆盖率 = 有索引的知识文件 ÷ 知识文件总数。
- **触发**：P2 开发、P4 规则、P5 血缘。
- **落盘**：`knowledge/**`、`knowledge/index/chunks.jsonl`。
- **现状**：16 个知识文件、6 条 chunk 索引（覆盖率 38%）；**产出尚未强制引用 chunk**——契约里没有 `knowledge_refs` 字段。

### C3 需求自动化

- **定义**：从原始需求到"可开工的规格"，机器能做的部分不让人做；人只回答歧义。
- **判据**：G0/G1 全自动判定；翻译稿的 8 段有 schema 约束（不只是文本存在性）；歧义项被打包成"一次性提问清单"，而不是反复往返。
- **触发**：需求文件落地到 `反馈者/`。
- **落盘**：`requirements/<需求>/反馈者/`、`需求分析员/`、`requirements/_registry.jsonl`。
- **现状**：G0（登记 + hash 对账）、G1（8 段 + 本体引用 + 可断言验收）已自动化并通过负向测试；翻译稿本身仍无 JSON 契约，只有 md 模板。

### C4 全过程留痕

- **定义**：每个动作留事件，每个产物留哈希，每个门禁留理由；任何时点可回放到"当时为什么这么定"。
- **判据**：journal 里 artifact 事件的 hash 与实际文件一致；每个门禁事件能指到检查输出的具体行；不存在"改了文件但没留痕"的产物。
- **触发**：每次写文件、每次过门禁。
- **落盘**：`journal.jsonl`、`contracts/journal_entry.schema.json`、`memory/decisions/`。
- **现状**：journal 46 条（28 artifact / 11 conversation / 7 gate），artifact hash 靠 `.tmp/gen_journal.py` 手工补；**没有写文件的钩子**，所以"忘记录"一定发生。

### C5 记忆体系

- **定义**：三层分工——运行记忆（journal/runs，短期）、决策记忆（ADR/rulings，中期、只增不改）、长期知识（knowledge/wiki，可修订但有 verified_by）。
- **判据**：每条决策能追到一次运行；每个知识点有验证者；过期条目（>90 天未被引用且状态 draft）会被巡检点名。
- **触发**：决策发生时写 ADR；每次运行结束做一次"晋升判断"。
- **落盘**：`memory/{decisions,rulings,reviews,lessons}`、`knowledge/wiki/`。
- **现状**：ADR-0001/0002 有余，lessons/reviews/rulings 基本空白；**没有晋升规则的可执行版本**（什么条件下 journal 的教训能变成 lessons）。

### C6 数据开发规范

- **定义**：命名、分层、分区、注释、幂等、质量规则全部可机器检查，且检查器就是规范本身（文档与代码不许两套说法）。
- **判据**：DDL/DML 各有校验器；规范页里的每条硬规则对应一条可执行检查；违规能被拦在门禁而不是评审会上。
- **触发**：P2 产出、P5 上线。
- **落盘**：`ontology/schema/`（元模型）、`skills/sk-sql-*/`、`knowledge/wiki/01-命名与词根.md`。
- **现状**：DDL 有校验器（列名 / 分区重复 / COMMENT / STORED AS / 单语句）；**DML 还没有**（sk-sql-dml 待建）；`gmv` 之类口径只在本体，规范页不重复——这条边界守住了。

### C7 定时驱动（wiki 更新 / 记忆更新 / 每周巡检）

- **定义**：把"该周期性做的事"从人的记忆里挪到调度器里：每周刷新 wiki 一致性、做一次记忆晋升与去重、跑一次全仓巡检并出报告。
- **判据**：三类任务有明确的 cron 表达式与产物路径；巡检报告能回答"本周哪里退化了"；连续两次巡检可对比出趋势。
- **触发**：定时（周级）。
- **落盘**：`runs/inspection/<YYYY-Www>/{report.md,report.json}`、`memory/reviews/`。
- **现状**：**完全没有**。今天所有检查都要人手敲，这也正是"开了新窗口就失忆"的根因之一。

## 三条必须守住的边界

1. **口径只在 ontology**。知识和记忆都不许定义"GMV 怎么算"；它们只能写"怎么写更省资源 / 上次这么写踩了什么坑"。自动积累最容易污染的就是这条线。
2. **自动到"待签"，不自动到"签"**。H1/H2/H3 是人的责任，机器可以准备好材料、给出建议，但不能替人签字。真要放开，必须走 `memory/rulings/waivers.json` 留痕。
3. **留痕不可编辑**。journal 只追加；写错了就再写一条更正，不能改历史。

## 四处冲突（现有设计 vs 这套思路）

| # | 冲突 | 建议 |
|---|---|---|
| X1 | C3 要"自动化"，但 G1 规定"待确认项非空不许开工"——自动跑必然撞上等人回答 | 允许"带条件开工"：非阻断歧义记入 `assumptions`，进 G2 由监督者复核；阻断歧义仍然停 |
| X2 | C2 要"知识自动积累"，但自动写容易把模型生的口径塞进 knowledge | 自动积累只写 `04_踩坑/` 与 `03_范例/`，且必须带 `source_ref`（哪次运行、哪条 journal）；口径一律走 ontology_delta |
| X3 | C7 要"定时"，但仓库目前零运行时（纯文件 + 手动脚本） | 巡检器先做成**单命令、零依赖**（`tools/inspect.py`），调度器只是外面套一层 cron/Airflow/DSH schedule，换载体不用改代码 |
| X4 | C4 要"自动留痕"，但没有文件系统钩子 | 退一步：产物类文件由**产物生成器**写 journal（谁生成谁记账），而不是靠人事后补 |

## 自动化分层（判断"做到哪一步了"）

| 层 | 含义 | 现在到哪 |
|---|---|---|
| L0 手工 | 靠文档和人 | 曾经是全部 |
| L1 可校验 | 有校验器，人跑 | ✅ 10 个校验器 |
| L2 可聚合 | 一条命令跑完全部检查并出结论 | ✅ `tools/inspect.py` |
| L3 可定时 | 调度器自动跑、结果留痕 | 未做 |
| L4 可自愈 | 发现问题能自动修（如重生成 dq_check.sql） | 局部（dq_to_sql） |

| M9 调度落地 | 周巡检 / wiki 刷新 / 记忆晋升 三条 cron 定义 + 载体适配 | 连续两周自动产出报告 |

## 巡检检查什么（M5 的口径）

分五组，全部只读、不改任何文件：

1. **门禁组**：跑现有 10 个校验器，逐项 PASS/FAIL，失败取首行原因。
2. **结构组**：目录是否符合"需求优先"、需求目录三角色是否齐、开发目录是否齐。
3. **闭环组**：每个需求走到哪个门（G0…G6）、缺哪一环、HITL 积压多久（如 G5 因 H3 未签已挂 N 天）。
4. **资产组**：本体状态分布、契约覆盖（有几份 schema / 设计要 9 份）、技能实现率、知识索引覆盖率。
5. **卫生组**：status: draft 超 90 天、孤儿目录、未留痕产物、空目录占位。

输出：`runs/inspection/<YYYY-Www>/report.md`（人看）+ `report.json`（下周对比用）。

## 待确认（会改变实现的三件事）

1. **运行载体**：角色是被 DSH 的 subagent 真跑，还是人对着文档执行、脚本只做校验？这决定 agents/*.md 要不要写成可加载的 preset。
2. **调度载体**：cron / Airflow / DSH 自带定时，选哪个？决定 M9 的产物形态。
3. **巡检的权限**：只出报告，还是允许自动提需求（如发现缺 DML 校验器就自动开一张 REQ）？决定要不要给巡检器写权限。
