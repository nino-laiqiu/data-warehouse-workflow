# 追踪：六类事件，只追加不修改

追踪不是"写日志"，是**把过程变成可回放的数据**。三个月后有人问"这版 SQL 为什么这么写"，答案必须在这份 journal 里找得到，而不是在某次会里。

落盘位置：`requirements/<需求目录>/需求开发员/journal.jsonl`，一行一个 JSON。契约：[`contracts/journal_entry.schema.json`](../contracts/journal_entry.schema.json)；写入口：[`tools/journal.py`](../tools/journal.py)。

## 六类事件

| type | 记什么 | 必填 | 一句话判据 |
|---|---|---|---|
| `conversation` | 问答记录 | `summary` | 人问了什么、结论是什么；**不存逐字原文**，只存决策 |
| `query` | 查询 SQL | `sql` `purpose` `result_summary` | 查了什么、为什么查、查出什么；SQL 全文进文件并算 `sql_hash` |
| `artifact` | 修改事件 | `path` `hash_after` | 哪个文件、改前改后哈希、改了什么（`diff_summary`） |
| `progress` | 进展 | `stage` `state` `summary` | 走到哪一步；`state` = started / done / blocked，blocked 必须写 `next`（卡在哪、等谁） |
| `todo` | 待办 | `text` `owner` `status` `todo_id` | 谁办、办什么、开着还是关了；关单追加同 `todo_id` 的 done/dropped |
| `gate` | 门禁 | `gate` `result` | G0–G6 / GA1–GA3 判定；fail/waived 必须写 `reason` |

## 三条硬规则

1. **只追加**。历史条目永不修改；写错了就追加一条 `supersedes: <旧 ts>` 更正。改历史等于伪造证据。
2. **不存原文只存摘要 + 引用**。整段对话贴进 journal，等于把仓库变成聊天记录仓库；存结论，原文靠 `refs` 指过去。
3. **不参与决策**。追踪者只记录别人做的决定；让它评判，它就会记对自己有利的版本。

## 日常用法

```bash
# 问答：这一轮定了什么
python tools/journal.py append --req <需求目录> --type conversation --actor chronicler \
  --summary "确认 GMV 按 pay_time 归日，退款不回冲" --refs requirements/<需求目录>/需求分析员/REQ-xxxx.md

# 查询：查了什么、查出什么（SQL 从文件读，不内联）
python tools/journal.py append --req <需求目录> --type query --actor requirement-translator \
  --sql-file .tmp/gmv_check.sql --purpose "核对近 30 天 GMV 与 ADS 是否一致" \
  --result "差异 0.003%，在阈值内" --engine hive --rowcount 1

# 修改：哪个文件改了
python tools/journal.py append --req <需求目录> --type artifact --actor developer-1 \
  --path requirements/<需求目录>/需求开发员/developer-1/sql/01_x.sql \
  --hash-before "" --hash-after <sha256> --diff "补了 dt 分区过滤"

# 进展：卡住或推进
python tools/journal.py append --req <需求目录> --type progress --actor chronicler \
  --stage P5 --state blocked --summary "G5 卡在 H3 放行" --next "等 nino 签字"

# 待办：开单 / 关单
python tools/journal.py append --req <需求目录> --type todo --actor chronicler \
  --todo-id T-20261128-01 --text "H3 上线放行签字" --owner nino --status open --due 2026-12-05
python tools/journal.py append --req <需求目录> --type todo --actor chronicler \
  --todo-id T-20261128-01 --text "H3 已签" --owner nino --status done

# 看现状
python tools/journal.py todos --req <需求目录>        # 未关闭的待办
python tools/journal.py show  --req <需求目录> --tail 10
python tools/journal.py check --req <需求目录>        # 全量校验（巡检也会跑）
```

## 待办编号

`T-YYYYMMDD-NN`，按开单日期编号，同一天从 01 递增。编号本身没有语义，唯一作用是把"开"和"关"连起来——**没有编号的待办永远关不掉**，因为它找不回自己。

## 为什么"进展"和"待办"要分开

- `progress` 回答"现在到哪了"，是**状态**，每次推进或卡住都写一条；
- `todo` 回答"还欠什么"，是**债务**，开一条就一直挂着，直到有人显式关掉。

只有 progress，会出现"看起来在推进，其实欠了三件事没人认领"；只有 todo，看不出当前卡点。两者都有，巡检才能算出"挂在 blocked 超过 5 天"和"待办积压"。

## 和巡检的关系

`tools/inspect.py` 会把每个需求的 journal 跑一遍 `check`，并统计：

- 未关闭待办数（积压是流程腐化的早期信号）；
- `blocked` 超过 N 天的进展（G5 挂 5 天就是这么发现的）。

## 历史条目里的旧角色名

`orchestrator`、`quality-officer` 这些角色在 2026-11-28 的 ADR-0003 里已经取消，但**历史 journal 不改**——它们是当时的真实记录。新条目一律用现在的 5 个角色 id。
