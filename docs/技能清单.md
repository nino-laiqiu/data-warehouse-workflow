# 技能清单

> 状态：**3 个已实现，12 个只有描述**（其中 `sk-spec-align` 不绑 stage，是 P3 之后的复核动作，所以 `check_skills.py` 只统计到 11 个待建）（用户 2026-11-28 决定：暂不实现，先把清单说清楚）。
> 判据列写的是"怎么算这个 skill 干对了"——实现前先有判据，否则写出来的只是脚本。

## 一个 skill 的最小骨架

```
skills/sk-<域>-<动作>/
├── SKILL.md        front matter: name / version / owner；正文写"什么时候用、怎么判定成功、失败怎么办"
├── schema.json     入参契约（JSON Schema 子集，用 tools/validate_contracts.py 校验）
└── validate.py     --input 契约 [--<产出> 路径] → 0/1 + 机器可读原因
```

三条纪律：**输入结构化、产出可脚本判定、可重复执行**。做不到这三条的，不是 skill，是 agent 的判断。

## 为什么这 11 个先不实现

1. **P2/P3 已经手工跑通一遍**（REQ-20261122-02 双轨 + 裁决），产物在里面，逻辑也写了；缺的是"把它固化成可重复调用的脚本"。
2. **A 线四个 skill 依赖对话界面**：没有入口，`sk-qry-intent` 只能拿手写问句测，测不出真实分布。
3. **判据比实现更贵**：11 个 skill 里最难的不是写 Python，是决定"什么算对了"。先把判据写下来，实现时不用返工。

## 什么时候该开始补

- 第二个需求需要**同样的 DML 体检** → 补 `sk-sql-dml`（重复劳动出现时）
- 双轨的**差异靠人肉眼比对超过 30 分钟** → 补 `sk-sql-diff`
- A 线**每天被问超过 5 次** → 补 `sk-qry-*` 四个

重复劳动是唯一可靠的信号；提前写等于猜需求。
