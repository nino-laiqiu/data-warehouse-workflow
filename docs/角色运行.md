# 角色怎么跑起来（运行载体 = DSH subagent）

一句话：**角色不是"写在 md 里的岗位说明"，而是一段能被 `subagent` 直接执行的提示词。**
定义在 `agents/roles.json`（机器可读），生成器是 `tools/role_prompt.py`，校验器是 `tools/check_agents.py`。

## 为什么不做成 DSH preset

DSH 的 agent preset 是"一个会话的人格与工具集"（bundle 里声明 `@deepseek-ai/dsh-agent-preset`，`plugins` 决定装哪些工具）。
我们这 5 个角色是**任务级**的：developer-1 和 developer-2 要并行、要互相看不见、跑完就退场。
把它们做成 5 个 preset 有三个代价：① 每个 preset 都要装一次 bundle，profile 里多 5 行插件；② `subagent` 没有"选 preset"的参数，preset 选了也没用；③ 角色会在同一次需求里切换，preset 换不了。

所以载体选 **subagent + 生成的提示词**：人格、边界、输入输出、硬规则，全部写在提示词里，一次生成、一次执行、可留痕。

## 怎么派活

```powershell
# 1) 先落下提示词（同时是"我真的这样派活"的证据）
python tools/role_prompt.py --role developer-1 --req 画像标签需求20261122 --write

# 2) 起一个 subagent，把提示词原文贴进 prompt，隔离靠 must_not_read
#    （派活的人用 subagent 工具，两个开发者同时起、互不等待）
```

`--json` 输出机器可读结构，编排脚本据此决定并发与顺序：

```json
{"role": "developer-1", "gate": "G2", "tools": ["read","write","edit","glob","grep","pwsh"],
 "must_not_read": ["requirements/画像标签需求20261122/需求开发员/developer-2/**"], "prompt": "..."}
```

### 顺序：谁必须等谁

派活顺序的唯一权威是 `flow/pipeline.yaml` 的 `depends_on`（不是文档里的段落顺序，机器读不出段落）。当前只有 P2 允许并行：

```
P0 → P1 → P2 ──┬─ developer-1 ─┐
               └─ developer-2 ─┴→ P3（监督者）→ P4 → P5 → P6
```

- **两个开发者同时起**，互不等待、互不可见。
- **等两轨都交付完**（每轨 = `sql/*.sql` + `design-notes.md` + `self-check.md`，经 G2），才起监督者。
- 监督者不参与开发、也不被开发者等待：它是这两个环节的**下一环**，不是第三个并行轨道。拿半成品比对，等于用不完整的信息做裁决。

这条约束有两道机器检查，不靠自觉：

| 检查 | 命令 | 拦什么 |
|---|---|---|
| 静态结构 | `python tools/check_pipeline.py` | 监督者所在 stage 声明了并行、或 `depends_on` 不含 P2（并行归属者）、或依赖倒序成环 |
| 派活时 | `python tools/chat.py task --role supervisor --req <需求目录>` | 两轨任一缺 `sql/`、`design-notes.md`、`self-check.md` 时直接拒绝，返回缺哪一项 |

## 5 个角色（编制见 ADR-0003）

| id | 阶段 | 门禁 | 一句话 |
|---|---|---|---|
| `requirement-translator` 需求分析员 | P0 / P1 / P4 / A5 | G1（P4 为 G4） | 收需求并登记、消灭歧义成 8 段、把验收标准变成可执行规则；A 线结论兼岗 |
| `developer-1` 开发者 1 | P2 / P5 | G2（P5 为 G5） | 双轨之一；裁决后隔离解除，由它落地血缘与调度 |
| `developer-2` 开发者 2 | P2 | G2 | 双轨之一，互不可见；P3 后退出 |
| `supervisor` 监督者 | P3 | G3 | 三层比对，出裁决与 final；只选不写 |
| `chronicler` 追踪者 | 全程 + P6 | —（G6 由它汇总） | 只追加记录；交付文档由它汇总（journal + final + 翻译稿） |

**为什么不再是 11 个**：登记、质量规则、血缘调度、交付文档都不需要独立角色——它们分别是需求分析员（定义侧）、开发者1（实现侧）、追踪者（记录侧）职责的延伸。加角色只增加交接次数，不增加信息量。

## 隔离怎么保证

- **规则层**：developer-1/2 的 `must_not_read` 互为对方目录，`tools/check_agents.py` 强制这条必须双向存在，删一条就报错。
- **产物层**：G2 要求两轨 SQL 的 sha256 **不相同**——如果两轨一模一样，说明有人偷看或都被同一份上下文带偏了。
- **记录层**：journal 里记的是 `actor`，跨轨读取会在"产物路径 vs actor 的 writes"对不上时暴露。

## 已知缺口

1. 提示词是"软约束"——模型仍然可能越界读文件。真硬隔离要在沙箱层做（每个 subagent 只挂载自己的目录），目前没做。
2. `agents/*.md` 只覆盖 4 个角色（developer-1/2 共用 `developer.md`），散文卡片是给人读的，机器只读 `roles.json`。
3. 同一需求重派角色会覆盖 `prompts/<role>.md`，旧版本只留在 journal 里——需要"提示词版本对比"时得自己 diff。
