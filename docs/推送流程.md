# 写入 GitHub 的流程

> 这份文档是给"下一个窗口的我"看的：新会话没有任何上下文，读完这页就能把文件写到 GitHub。
> 最后验证：2026-11-26，提交 `96b066f` 起可用（脚本与本文档同一提交更新）。

## 一句话

```powershell
& .\tools\push.ps1 -Message "feat: 改了什么" -All
```

不用 `git push`，一条命令完成：读凭据 → 收集改动 → 走 Git Data API 提交 → 打印提交链接。

## 为什么不用 git push

不是习惯问题，是这台机器上 `git push` 走不通，且有据可查：

| 现象 | 真实原因 |
|---|---|
| `Failed to connect to github.com port 443 after 21073 ms: Timed out` | 网络到 github.com:443 不稳定，时好时坏 |
| `OpenSSL SSL_read: Connection was reset, errno 10054` | 同上，TLS 握手被重置 |
| `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS` | Windows schannel 在沙箱里拿不到凭据，必须 `-c http.sslBackend=openssl` |
| `sh: couldn't create signal pipe, Win32 error 5` → `could not read Username` | git 为了弹凭据提示去 spawn `sh`，沙箱禁止建管道 |
| `git: 'Basic' is not a git command` | 把 `-c http.…extraheader=Authorization: Basic xxx` 写在参数里，被 argv 按空格重切 |

`api.github.com` 一直稳定，所以**写入一律走 API**。这是用户 m01395 定的规矩，不是临时方案。

## 前置条件（三条，缺一条就跑不通）

1. **node**：`F:\node\node.exe`（v18.19.0）。系统 PATH 里的 node 版本可能更老，脚本默认用这个全路径。
2. **token**：`C:\Users\nino\.dsh\.credentials.yaml` 里的 `GITHUB_MCP_PAT`，是 **classic PAT（40 字符，repo scope）**。
   - fine-grained PAT 不行：它只能操作已存在仓库，建不了仓；且 Contents 权限若是 read，写文件报 403。
   - `tools/push.ps1` 会自己读这一行，不需要你手动传。
3. **repo**：`nino-laiqiu/data-warehouse-workflow`，分支 `main`，**public**。

## 日常用法

```powershell
# 1. 推送所有未提交改动（最常用；自动把删除识别成远端删除）
& .\tools\push.ps1 -Message "feat: 新增推送流程文档" -All

# 2. 只推指定文件（不依赖 git 状态，文件没被 add 也能推）
& .\tools\push.ps1 -Message "docs: 改 README" -Files README.md,docs/推送流程.md

# 3. 删除远端文件：清单里路径前面加减号
& .\tools\push.ps1 -Message "chore: 删除废弃文件" -Files "-old/file.md"

# 4. 只改一个文件、想少打字（走 Contents API，另一个脚本）
$env:GITHUB_TOKEN = <token>
F:\node\node.exe tools/push_file.mjs README.md README.md "docs: update"
```

`-All` 的收集逻辑：`git -c core.quotepath=false status --porcelain` → 未跟踪目录递归展开 → 状态含 `D` 的转成 `-路径` → 跳过 `.tmp/` 与 `__pycache__`。

**调用方式必须是 `& .\tools\push.ps1 ...`（当前会话里直接执行）。**
不要写成 `pwsh -File tools/push.ps1`：沙箱禁止嵌套启动 pwsh，会报
`程序'pwsh.exe'运行失败： Access to the path '\\.\pipe\LOCAL\dotnet_…' is denied` + `[sandbox: file access denied under workspace-write mode]`。

一次成功推送的真实输出长这样：

```

  docs/推送流程.md
  tools/push.ps1
基提交 7204dbf (feat(M4): 画像标签需求 P4-P6 闭环)
  blob docs/推送流程.md 6432B

OK main -> 8a58a69（2 个文件）
https://github.com/nino-laiqiu/data-warehouse-workflow/commit/8a58a69
```

## 底层发生了什么

`tools/push_batch.mjs` 用的是 Git Data API，**一次提交、原子生效**：

```
GET  /git/ref/heads/main                    → 拿到父提交 sha
GET  /git/commits/{parent}                  → 拿到父 tree sha
POST /git/blobs        × N                  → 每个文件上传成 blob（base64）
POST /git/trees        { base_tree, tree }  → 新 tree，含变更/删除（sha:null）
POST /git/commits      { message, tree, parents }
PATCH /git/refs/heads/main { sha, force:false }
```

为什么不用逐个文件 Contents API：N 个文件会产生 N 个提交，中间失败会留下半成品；tree 一次提交要么全成要么全不成。

`force: false` 意味着**不会覆盖别人推的新提交**——如果远端在你推送期间前进了，会直接失败而不是静默丢代码。

## 推完之后：本地对齐

API 提交算出来的 sha 和本地 git 提交的 sha **天然不同**（作者时间、父提交等元数据不一样）。想让 `git status` 干净、`git log` 跟远端一致：

```powershell
# 1. 先 fetch（需要认证，走环境变量，别写在参数里）
$env:GIT_CONFIG_COUNT = 3
$env:GIT_CONFIG_KEY_0 = 'credential.helper';            $env:GIT_CONFIG_VALUE_0 = ''
$env:GIT_CONFIG_KEY_1 = 'http.sslBackend';              $env:GIT_CONFIG_VALUE_1 = 'openssl'
$env:GIT_CONFIG_KEY_2 = 'http.https://github.com/.extraheader'
$env:GIT_CONFIG_VALUE_2 = "Authorization: Basic $([Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("x-access-token:$token")))"

git fetch origin main --depth=1
# 2. 只有 fetch 真的成功了，才执行下一条
git reset --hard origin/main
```

**血泪教训（2026-11-22 真实事故）**：一个脚本里 fetch 超时没人检查返回值，紧接着执行了 `git reset --hard origin/main`，HEAD 退回旧提交，**把所有未提交的源码改动抹掉了**。恢复只能靠 API 把整个 tree 拉回来重提交。

结论：`fetch` 与 `reset --hard` 永远分两条命令、人工确认。fetch 失败就什么都别做，本地继续攒着，反正 API 通道不依赖本地 git 状态。

**顺带一个正常现象**：API 推送不会更新本地 git 索引，所以推完 `git status` 里那批文件**还是 `??` 未跟踪状态**。这不是失败；再跑 `-All` 会把它们再列一遍（内容相同，GitHub 上不会产生 diff 之外的变化）。想让本地干净，就等 fetch 成功之后 `reset --hard`。

## 失败排查

| 报错 | 原因 | 处理 |
|---|---|---|
| `ERROR: 缺少 GITHUB_TOKEN` | 直接调了 `push_batch.mjs` 没设环境变量 | 用 `push.ps1`，或先 `$env:GITHUB_TOKEN = ...` |
| `401 Unauthorized` | token 抄错/过期 | 用 `GET https://api.github.com/user` 验证一遍（先验证再推送，别猜） |
| `403 Resource not accessible` | 权限不足（fine-grained 只读 / 不是该仓的 collaborator） | 换 classic PAT（repo scope） |
| `404 Not Found` | repo 名写错，或 token 无权限看私有仓 | 检查 `GITHUB_REPO` |
| `读不到文件 xxx` | 路径写错 / 用了 Windows 反斜杠 | 清单里统一用 `/` |
| `PATCH /git/refs… -> 422` | 远端在这期间前进了（`force:false` 生效） | 重新跑一次，脚本会以新 HEAD 为父提交 |
| `token length: 93` 且 401 | 误用了 fine-grained | 换成 40 字符 classic |

## 新窗口冷启动清单

1. 在当前 pwsh 会话里直接执行（**不要** `pwsh -File`，沙箱禁止嵌套 pwsh）：
   `& .\tools\push.ps1 -Message "test: 连通性" -Files README.md`
   能打印 `OK main -> <sha>` 和提交链接，就说明通道正常。
2. 不能推就按上面四条前置条件逐个查（node → token → repo → 网络）。
3. **不要**回头去试 `git push`：它在这台机器上大概率还是超时，试一次要等 21 秒。
4. 改脚本时注意：`Start-Process -PassThru -Wait` 返回的对象在本机 **`ExitCode` 是空值**
   （不是 0），拿它判成败会把成功当失败（`$null -ne 0` 为真）。判断一律看输出文件内容。

## 红线

- 不把 token 写进任何提交、文档、日志。
- 不 `git push --force`，也不 `PATCH /git/refs` 时 `force: true`。
- 不在 fetch 失败后执行 `reset --hard`。
- 提交信息写清"改了什么 + 为什么"，别写"update"。
