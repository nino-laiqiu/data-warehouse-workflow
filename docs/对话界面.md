# 对话界面

> 状态：**P1 已实现并实测**（`tools/chat.py`：CLI + 同契约的本地 HTTP，四端点全部跑通）。
> 本文回答"对话界面是什么、挂在哪、要提供哪几个动作"，不做前端设计。

## 一句话

对话界面是**人进入这套工作流的唯一入口**：分析师在里面问数，需求方在里面答口径，开发者在里面派活。
它本身不产生知识、不改口径、不跑 SQL——它只负责把人的话变成契约里的字段，再把结果翻成人话。

## 为什么它比"补齐 11 个 skill"更靠前

skill 是被**调用**的，不是被**使用**的：`sk-qry-gen` 要有 A3 的意图契约才能跑，`sk-req-validate` 要有
需求分析员的翻译稿才能跑。而没有对话界面，这些契约只能靠人在命令行里手工拼——skill 写得再多也没有入口。

所以顺序是：**先有入口（界面 + 契约），再补执行（skill）**。

## 三个入口场景

| 场景 | 谁在用 | 背后走什么 | 现有可复用件 |
|---|---|---|---|
| 取数问答 | 数据分析师 | A 线 A1–A6 | `tools/qa_store.py`、`docs/问答采集接口.md` |
| 口径澄清 | 需求方 / 需求分析员 | `req_review.py` 的 ask / answer / round | `requirements/<需求>/需求分析员/_review/*.json` |
| 派活与验收 | 开发者 / 监督者 | `role_prompt.py` → subagent → 回收产物 | `agents/roles.json`、`journal.py` |

三者共用一条链路：**人说话 → 落事件 → 走 stage → 门禁 → 回话**。

## 接口草案（四个动作就够）

```
POST /v1/chat                 { session_id, question }                    → { answer, run_id, sql?, caveats[] }
POST /v1/review/{req_id}/answer { qa_id, text, by }                       → { open_blocking, status }
GET  /v1/run/{run_id}/journal?type=gate|progress|todo                     → { events[] }
POST /v1/task                 { role, req_id, stage, instruction? }       → { run_id, prompt_path }
```

约定：

1. `/v1/chat` 每轮**必须**落一条 `qa_record`（走采集接口，断网落 outbox），因为问答是最值钱的知识原料。
2. `/v1/review/*` 只是 `req_review.py` 的 HTTP 皮——状态机与硬规则在脚本里，界面不许绕过。
3. `/v1/task` 只**生成提示词并派活**，不直接改产物；产物由角色写、门禁验。
4. 所有响应带 `caveats[]`：A 线回答必须能自证（数据截止日、口径来源、命中哪条知识），不许只有结论。

## 三种形态，按投入递增

| 形态 | 说明 | 成本 | 建议 |
|---|---|---|---|
| CLI | `python tools/chat.py "近30天各渠道GMV"` | 半天 | 先做，验证契约 |
| Web 聊天 | 单页 + 上述四端点 | 2–3 天 | 第二阶段 |
| IM 机器人 | 钉钉/飞书 webhook 转 `/v1/chat` | 1 天 | 有需求再接 |

> DSH 自己就有一个 Web 界面，可以直接当"开发者入口"用；`/v1/chat` 更像给**分析师**的专用入口——
> 分析师不该看见 agent 名字、run 目录、契约字段，只看见问题和答案。

## 最小可用（MVP）的判定

一个版本算"有对话界面了"，需要同时满足：

1. 分析师能提问并拿到带 `caveats` 的回答，且**SQL 可见**（不可见的答案不可信）。
2. 每轮问答自动进 `qa_turn`，`stats` 能看到会话数增长。
3. 需求方能在界面上回答阻断问题，答完 `req_review.py status` 的 `open_blocking` 归零。
4. 界面上能看见这条需求的门禁状态与未关待办（读 `journal.py`，不写）。

## 不做什么（有意的）

- **不做**自由聊天窗口：界面必须收敛到"问数 / 答口径 / 派活"三类动作，否则会退化成通用 chatbot。
- **不做**在界面上改口径：口径只能改本体（人改），界面最多发起 `ontology_delta` 提案。
- **不做**把 agent 的中间步骤全暴露给分析师：只给结论 + 证据 + 口径来源。
- **不做**前端权限系统：先靠"谁能登进这个页面"区分，RBAC 等有真实多租户再说。

## 实现现状（P1）

`tools/chat.py` 一个文件同时是 CLI 和 HTTP 服务，动作与端点一一对应：

| 命令行 | 端点 | 实测结果 |
|---|---|---|
| `python tools/chat.py chat "近30天城市等级支付用户数"` | `POST /v1/chat` | 出 SQL（`NVL(d.city_level,'UNKNOWN')` + `COUNT(DISTINCT p.user_id)`），4 条 caveats |
| `python tools/chat.py review answer --req-id … --id Q9 --text …` | `POST /v1/review/{req}/answer` | 已确认的需求被**拒绝**（`ok=false`），必须先 `reopen` |
| `python tools/chat.py journal --run R-1 --type gate` | `GET /v1/run/{run}/journal?type=` | `type=gate` 只回 8 条 gate 事件（全量 58 条） |
| `python tools/chat.py task --role developer-1 --req … --stage P2` | `POST /v1/task` | 生成 `需求开发员/prompts/developer-1.md` |

四条 caveats 是固定结构：引擎（规则匹配，非 LLM）、时间窗、结果未执行、口径提醒
（用 `dim_user_df.city_level` 时追加"这是注册地不是收货地址，见 T-20261128-02"）。

三个写进代码的硬约束：

1. **宁可不答也不编 SQL**：`guard_sql` 六条（只读、必须有 `${dt}`、禁 `SELECT *`、JOIN ≤3、必须有 LIMIT、禁写关键字）任一不过就 `refused=true`，退出码 3。
2. **已确认的需求不能直接改答案**：`req_review.py answer` 在 `status=confirmed` 时直接拒绝——这条是踩出来的（冒烟测试把 Q9 的答案覆盖成了 `x`，再从 `_history` 恢复）。
3. **采集失败不拖垮问答**：`qa_store` 写入失败只追加一条 caveat，回答照常返回。
