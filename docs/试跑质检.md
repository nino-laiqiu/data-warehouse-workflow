# 试跑质检（P3B / G3B）

> 位置：`P3 监督比对 → G3 → **P3B 试跑质检 → G3B** → P4 质量规则 → P5 血缘调度 → P6 交付`

## 为什么插在监督者后面

G3 通过只说明"两份实现里选得对"，不说明"这份 SQL 跑得动"。如果不在这里拦，问题会在两个更贵的地方暴露：P5 排期上线时炸，或者上线后由业务发现数据是空的。

所以：**裁决通过 → 立刻拿去跑一遍 → 跑得动再谈质量规则和排期**。这是全流程里唯一一处"真连环境"的自动门禁。

## 三态：passed / failed / blocked

| verdict | 含义 | G3B |
|---|---|---|
| `passed` | 环境连通、每条脚本 `executed` 或 `explained`、结果类检查全过 | 过 |
| `failed` | 连上了但解释/执行/质检失败 | 不过，退回 P3 修 `final/` |
| `blocked` | 没连环境（没有 `HQL_CMD` / 没权限 / 库不存在） | 不过；只能靠 `waiver` 由人签放行，且必须记待办 |

**blocked 不是通过。** 它表示"没有环境证据"。把 blocked 写成 passed，等于把最贵的判断交给运气。

## 怎么跑

```powershell
# 1) 离线：只出计划，不产生证据（verdict=blocked，G3B 不会过）
python tools/trial_run.py --req 画像标签需求20261122

# 2) 沙箱真跑：HQL_CMD 的写法与 verify_live 一致（命令前缀，SQL 作为最后一个参数）
$env:HQL_CMD = "beeline -u jdbc:hive2://sandbox:10000/default -n etl -e"
python tools/trial_run.py --req 画像标签需求20261122 --mode sandbox --target dw_tmp_profile --dt 20261127
python tools/trial_run.py --req 画像标签需求20261122 --mode sandbox --target dw_tmp_profile --dt 20261127 --execute

# 3) G3B 门禁（只验报告，不跑引擎）
python tools/trial_run.py --req 画像标签需求20261122 --check
```

- 默认只 `EXPLAIN`（不写数据，最便宜的"跑得动"证据）；`--execute` 才真执行 DDL/DML，并触发结果类检查。
- **目标库必须是沙箱**：名字含 `tmp` / `shadow` / `sandbox` / `dev` / `test` / `stg` / `试跑` 之一。不像沙箱直接判 blocked，加 `--allow-prod` 也只会把风险写进 `notes`，G3B 仍不放行。
- 结果类检查：目标表当日行数、主键唯一（取 `dq_rules.json` 的 unique 规则）、与上游对账（取 reconcile 规则）。

## 产物

```
requirements/<需求目录>/需求开发员/试跑/
├── 试跑报告.json     # 契约 contracts/trial_run.schema.json（stage=P3B）
└── 试跑报告.md       # 给人看的同一份内容
```

报告里每条脚本记 `sha256`——试跑之后 `final/` 又被改过，hash 对不上就该重跑，而不是沿用旧证据。

## 为什么不用现网验证（P6）代替

`verify_live` 是**上线前最后一道**：它拿 DQ 断言打生产库，签 G5。而这里要回答的是更早的问题："这版 SQL 在引擎里能不能跑、写进去有没有数据"。两者的环境、时机、代价都不同：

| | P3B 试跑 | P6 现网验证 |
|---|---|---|
| 何时 | 裁决后立刻 | 交付前 |
| 打哪个库 | 沙箱 | 生产（只读 SELECT） |
| 代价 | 分钟级，可反复 | 需要权限与窗口 |
| 失败意味着 | 回去改 SQL（便宜） | 叫停上线（贵） |
