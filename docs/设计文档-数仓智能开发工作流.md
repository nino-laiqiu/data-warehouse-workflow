## 0. 阅读指引与本文边界

**本文回答三个问题：**
1. 这套工作流由哪些部件构成，每个部件的**唯一职责边界**是什么；
2. 八阶段的**输入契约、产出契约、门禁规则**分别是什么；
3. 以电商交易域为例，一条需求从自然语言走到可上线 SQL 和画像标签宽表，**长什么样、错在哪、怎么验收**。

**本文不做的事：**
- 不写最终代码（skills 脚本、agent 提示词全文下一阶段产出）；
- 不承诺具体调度平台（Airflow / DolphinScheduler / DataWorks 均可对接，接口见 §7.7）；
- 不涉及实时链路（Flink 实时成交看板），本文只覆盖 T+1 离线数仓；实时化在 §11 作为 M5 扩展项列出。

**读者定位：** 数据架构师 / 数仓负责人评审可行性与边界；开发同学看 §7、§9 直接照做；算法同学看 §4、§6 的检索与编排设计。

## 1. 问题与目标

### 1.1 现状痛点

数仓开发的真实成本，80% 不在写 SQL，而在写 SQL 之前的四件事：

| 痛点 | 表现 | 后果 |
|---|---|---|
| **口径不可判定** | "GMV"三个人给出三个算法：含不含运费、退款回不回冲、按支付日还是下单日 | 报表对不上，复盘会变成对数会 |
| **模型不可复用** | 每个需求建一张宽表，同名字段不同含义，同含义字段不同名 | 表数量膨胀，血缘断裂，无人敢下线 |
| **规范不可执行** | 命名规范写在 Wiki 里，评审靠人眼，新人第一周必踩 | 规范文档 100% 存在，符合率 40% |
| **知识不可沉淀** | 老员工知道"华为通道回执延迟 5~30 分钟，凌晨批次会跨天"，但没写下来 | 同一个坑每半年踩一次 |

用 LLM 直接生成 SQL，会把这四个问题同时放大：LLM 会"善意地"补全不存在的字段、"合理地"发明口径、"流畅地"违反规范。所以工作流的核心不是"让 LLM 更会写 SQL"，而是**给 LLM 造一个不能乱来的约束环境**。

### 1.2 设计目标

| 编号 | 目标 | 可验证判据 |
|---|---|---|
| G-1 | 口径唯一 | 任一指标在全链路只有一个定义源，出现第二处即门禁失败 |
| G-2 | 结构可复用 | 新需求优先复用一致性维度，新建维度需本体评审 |
| G-3 | 规范可执行 | 规范以脚本可判定的形式存在，不依赖人眼 |
| G-4 | 知识可沉淀 | 每次 run 的优质产物、踩坑结论自动回流知识库 |
| G-5 | 产物可重放 | 给定「本体版本 + 知识库版本 + skill 版本 + 模型版本」四元组，可复现同一套产物 |
| G-6 | 人工可介入 | 关键节点 HITL，人工可否决/豁免，但豁免必须留痕 |

### 1.3 非目标

- 不做"一句话生成整个数仓"的黑盒；本工作流明确接受**人在环路**。
- 不做通用的 NL2SQL 工具；只服务数仓分层建模这一条链路。
- 不替代数据治理平台；本体是治理的输入，不是治理平台本身。

## 2. 总体架构：四支柱 + 编排层

### 2.1 分层图

```
┌───────────────────────────────────────────────────────────────────┐
│  编排层  flow/                                                     │
│  状态机 · 阶段门禁 · 回退边 · HITL 卡点 · 产物指纹                  │
├───────────────────────────────────────────────────────────────────┤
│  角色层  agents/                                                   │
│  编排器 │ 需求分析 │ 本体管理 │ 建模师 │ 指标管理 │ 开发 │ 质量官 │ 审计 │
├───────────────────────────────────────────────────────────────────┤
│  能力层  skills/                                                   │
│  每阶段若干原子动作，每个动作 = 输入契约 + 模板 + 执行器 + 校验器   │
├───────────────────────────────────────────────────────────────────┤
│  上下文层  knowledge/                                              │
│  规范 │ 方言函数手册 │ Few-shot 范例 │ 踩坑库 │ 历史优质产物        │
├───────────────────────────────────────────────────────────────────┤
│  事实层  ontology/                                                 │
│  对象 ObjectType │ 过程 ProcessType │ 指标 MetricType │ 关系 │ 约束 │
└───────────────────────────────────────────────────────────────────┘
                         ↑ 唯一事实源，可脱离 LLM 独立审计
```

### 2.2 四支柱的职责与失效后果

| 支柱 | 本质 | 唯一职责 | 明确不负责 | 缺失后果 |
|---|---|---|---|---|
| **业务本体** | 事实源 | 定义"世界上有什么、怎么算、叫什么" | 不存 SQL、不存规范、不存提示词 | 口径漂移，指标同名不同义 |
| **LLM 知识库** | 上下文供给 | 提供规范、方言能力、范例、历史经验 | 不定义口径（口径只在本体） | LLM 写"看起来对"的 SQL，风格漂移 |
| **Skills** | 原子能力 | 把一件**可判定对错**的动作固化 | 不做跨阶段决策 | 每次自由发挥，不可复现 |
| **Agents** | 角色与权责 | 按角色分工、按权限读写 | 不内联业务规则（规则在 skills/本体） | 一个 agent 既写又审，自证清白 |

### 2.3 单向依赖原则（本设计的核心约束）

```
agents → skills → (ontology, knowledge)
flow   → agents
ontology ⊥ LLM        # 本体不依赖 LLM 也能被读懂、被校验、被版本管理
```

三条硬规则：

1. **只有本体管理 agent 拥有 ontology/ 的写权限**，其余角色一律只读。建模师想新增维度，只能提交 `ontology_delta` 提案。
2. **skills 不写本体、不写知识库**，只产出候选产物与校验报告。知识库回流由编排层在 run 结束后统一执行。
3. **flow 不含业务判断**，只做状态推进与门禁裁决；"该不该建这张表"属于建模师，"能不能过"属于门禁。

### 2.4 为什么不是"一条长提示词链"

| 方案 | 问题 |
|---|---|
| 单条超长提示词 | 上下文窗口装不下 8 阶段全部规范；改一处全崩；无法定位失败环节 |
| 纯文档规范 + 人工评审 | 规范符合率靠自觉；评审成本高；无法规模化 |
| 纯脚本工程（dbt 风格） | 结构化能力最强，但无法处理"从模糊需求到模型"这一段非结构化工作 |
| **本方案：契约化流水线** | 每阶段产物是机器可校验的结构化文件，LLM 只负责阶段内推理，阶段间用契约交接而非自然语言 |

**关键取舍：阶段之间不用自然语言交接。** 自然语言交接是 LLM 幻觉的主要入口——上游说"按天聚合"，下游就可能脑补出 `dt` 分区和 `day` 字段两套写法。用 JSON Schema 交接，字段缺失就是硬失败，而不是"看起来差不多"。

### 2.5 双场景：同一底座，两条泳道

本工作流服务两类人，他们的**起点不同、失败代价不同、门禁强度也必须不同**：

| 维度 | **A 线：取数分析** | **B 线：数仓开发** |
|---|---|---|
| 使用者 | 数据分析师、运营、业务方 | 数仓开发工程师 |
| 起点 | 一个业务问题："上周各渠道 GMV 为什么跌了 3%" | 一个数据需求或指标上线 |
| 终点 | 可复查的 SQL + 结论 + 口径说明 | 可上线的表 + 指标 + 血缘 + 文档 |
| 单次耗时 | 分钟级（目标一轮问答 <60 秒） | 天级到周级 |
| 失败代价 | 结论错 → 一次决策错 | 数据错 → 全公司报表错 |
| 门禁强度 | 轻，3 道（GA1~GA3） | 重，8 道（G1~G8） |
| 能否写本体 | ❌ 只读 | ✅ 仅通过 delta 提案 |
| 产物 | 查询模板、分析结论、口径说明 | DDL/DML、DQ 规则、血缘、数据字典 |
| 频率 | 高频、长尾、不可预测 | 低频、计划内、有排期 |

**共享约 80%：** 同一份本体、同一个知识库、同一批 SQL 校验规则、同一套契约思想。
**分化约 20%：** 起点解析方式、门禁强度、产物形态。详见 §7.0 与 §7.1。

> A 线**不是** B 线的简化版。A 线的难点是「歧义消解 + 可信度自证」（我算的这个数凭什么可信），B 线的难点是「结构正确 + 可重跑」。用 B 线的重型门禁套 A 线，分析人员会直接绕开工具回去手写 SQL；用 A 线的轻门禁套 B 线，等于没有门禁。

## 3. 支柱一：业务本体 Ontology

### 3.1 定位

本体回答四个问题，且**只回答这四个**：

1. 业务里有哪些**对象**（用户、商品、订单、店铺、渠道…）？
2. 业务里发生了哪些**过程**（下发、到达、点击…），每个过程的**粒度**是什么？
3. 有哪些**指标**，每个指标的**口径**（分子/分母/聚合/限定）是什么？
4. 对象与对象、过程与对象之间的**关系**与**约束**是什么？

> 判断标准：如果一个信息不能用"对象/过程/指标/关系/约束"这五类之一表达，它就不该进本体（应该进知识库或规范文档）。这条标准能挡住 90% 的本体腐化。

### 3.2 元模型（Meta-Model）

本体自身也需要 schema。五类节点，统一带 ID、版本、状态、责任人：

```yaml
# ontology/schema/meta-model.yaml（元模型的元模型，节选）
version: "1.0"

node_common:            # 所有节点的公共字段
  id:         { type: string, pattern: "^[A-Z][A-Z0-9_]{2,63}$" }
  name_cn:    { type: string }
  desc:       { type: string }
  owner:      { type: string }              # 责任人，必填
  status:     { enum: [draft, active, deprecated] }
  version:    { type: string }              # 语义化版本，口径变更必须升 version
  created_at: { type: date }
  tags:       { type: array, items: string }

object_type:            # 业务对象（Kimball 的 dimension 来源）
  extends: node_common
  properties:
    business_key:    { type: array, items: string }   # 业务主键，如 device_id
    attributes:      { type: array, items: attribute }
    consistency:     { enum: [conformed, local] }     # 是否一致性维度
    scd_type:        { enum: [none, type1, type2] }
    pii_level:       { enum: [none, low, high] }      # 合规分级，决定脱敏策略
    source:          { type: array, items: string }   # 上游表

process_type:           # 业务过程（Kimball 的 business process，一个过程对应一张事实表）
  extends: node_common
  properties:
    grain:           { type: array, items: string }   # 粒度声明，必填且唯一
    events:          { type: array, items: string }   # 过程内事件枚举
    measures:        { type: array, items: measure }
    fact_table:      { type: string }                 # 落地的 DWD 事实表
    additive:        { enum: [full, semi, none] }

metric_type:            # 指标（OneData：原子 / 派生）
  extends: node_common
  properties:
    level:           { enum: [atomic, derived] }
    process_ref:     { type: string }                 # atomic 必填：所属业务过程
    measure_ref:     { type: string }                 # atomic 必填：引用的度量
    aggregation:     { enum: [count, count_distinct, sum, max, min] }
    numerator_ref:   { type: string }                 # derived 必填：分子指标
    denominator_ref: { type: string }                 # derived 必填：分母指标
    modifiers:       { type: array, items: string }   # 修饰词，如 android / hms / 营销场景
    time_window:     { enum: [1d, 7d, 30d, natural_month] }
    caliber:         { type: string }                 # 口径自然语言描述，必填
    coverage:        { type: string }                 # 数据可测性说明（如 APNs 无展现回执）
    forbidden_as:    { type: array, items: string }   # 禁止被当作什么用（防误用）

link_type:              # 关系
  properties:
    from_ref, to_ref: { type: string }
    cardinality:      { enum: ["1:1", "1:N", "N:M"] }
    bridge_table:     { type: string }                # N:M 必须有桥接表

constraint:             # 约束（可执行）
  properties:
    kind:      { enum: [unique, not_null, enum_set, range, monotonic, referential, cross_table] }
    target:    { type: string }
    expr:      { type: string }                       # 可执行表达式
    severity:  { enum: [block, warn] }
```

### 3.3 存储与版本策略

| 项 | 决策 | 理由 |
|---|---|---|
| 源格式 | **YAML（一人一文件，git 管理）** | 可 diff、可 review、LLM 易读、无需数据库依赖 |
| 校验 | JSON Schema + 自定义校验器 | 提交前拦截，不靠人眼 |
| 查询 | 加载为内存图 / 导出 CSV / 可选导出 OWL | 按需，不预先引入图数据库 |
| 版本 | 本体整体打 tag（如 `v1.4.0`），指标口径变更单独升 `version` | 产物可重放需要精确版本锚点 |
| 变更 | 只能通过 `ontology_delta` 提案 → 评审 → 合并 | 防止 agent 直接改事实源 |

**为什么不用 Neo4j/OWL 起步：** 图数据库解决的是"复杂多跳查询"，而数仓本体的主要消费方式是"按 ID 精确取一个指标的定义"和"按阶段取一组对象"，YAML 足够。引入图库会带来部署、备份、权限、同步四类运维成本。**这是有意为之的延后决策**，见附录 C。

### 3.4 本体校验器规则（提交即校验）

| 规则 ID | 校验内容 | 严重级 |
|---|---|---|
| O-01 | ID 全局唯一，符合命名正则 | block |
| O-02 | 每个 `process_type` 有且仅有一个 `grain` 声明 | block |
| O-03 | 每个 `atomic` 指标必须引用已存在的 `process_type` 与 `measure` | block |
| O-04 | 每个 `derived` 指标必须同时有 `numerator_ref` 与 `denominator_ref`，且分子分母**粒度相同、时间窗相同** | block |
| O-05 | `derived` 指标的 `modifiers` 必须在修饰词字典中已注册 | block |
| O-06 | `deprecated` 节点不得被 `active` 节点引用 | block |
| O-07 | 每个 `object_type` 的 `pii_level=high` 必须有脱敏策略标签 | warn |
| O-08 | `consistency=conformed` 的维度必须有唯一的 `dim_` 落地表 | warn |
| O-09 | 指标 `caliber` 不得为空、不得少于 20 字 | block |
| O-10 | 同一 `(process, modifiers, time_window)` 组合下不允许存在两个语义相同的指标（同义冲突检测） | warn |

> O-04 是整个本体最值钱的一条规则。数仓里 70% 的口径争议，本质是分子分母粒度不一致（分子是点击明细去重、分母是发送记录不去重）。这条规则把它变成机器可判定的错误。

### 3.5 电商交易域本体实例（节选，完整版见 §9.1–§9.2）

三个文件，分别代表"是什么"（对象）、"发生了什么"（过程）、"怎么算"（指标）。注意每个文件里最关键的不是字段名，而是 `description` 和 `caliber`——那才是 LLM 猜不到、必须由人钉死的部分。

```yaml
# ontology/object/order.yaml
id: ORDER
name: 订单
description: 一次交易的主单据，一笔订单可含多个 SKU。订单金额是「应付」，不是「实付」，实付要看支付流水
```

### 4.3 Chunk 元数据规范

每个知识片段必须自带元数据，否则检索必然串味（把 MySQL 的分页语法塞进 Hive 任务）：

```yaml

version: 1.4

```

### 4.4 检索策略：先过滤，再检索

检索不是"把 top-k 塞给模型"，而是分四步：

```
① 硬过滤   stage ∈ chunk.stages  AND  engine ∩ {hive,spark} ≠ ∅  AND  trust ≠ deprecated
② 混合召回  BM25(关键词) ∪ 向量(语义)，各取 top-10，RRF 融合
③ 冲突消解 trust=authoritative 优先；同 trust 取 version 高者；仍有冲突写入 conflict_log
④ 预算装配 按阶段 token 配额截断，规范类必选（不参与截断），范例类按相似度选
```

**各阶段检索配额（token 预算）：**

| 阶段 | 必选（不截断） | 可选上限 | 说明 |
|---|---|---|---|
| 需求受理 | 无 | 2k | 主要靠人给的资料 |
| 本体对齐 | 元模型 + 该域全部对象/过程 | 3k | 本体本身是主上下文 |
| 维度建模 | modeling_kimball.md + 总线矩阵历史 | 6k | 需要范例参考 |
| 指标定义 | metric_onedata.md + 该域已有指标 | 4k | 防重复造指标 |
| SQL 生成 | sql_style.md + hive_functions.md | 12k | 配额最大，范例最关键 |
| 质量规则 | 04_踩坑/ 全部 | 4k | 规则来自踩坑 |
| 血缘调度 | layering.md | 2k | 结构化为主 |
| 文档交付 | naming.md | 3k | 模板驱动 |

> 为什么 SQL 生成给到 12k：这是唯一一个"范例质量直接决定产出质量"的阶段。Few-shot 里的去重、除零、分区写法，比任何规范条文都管用。

### 4.5 知识回流机制

每次 run 结束，编排层执行三件事：

1. **产物归档**：`runs/<run_id>/` 全量归档，含四元组指纹；
2. **候选回流**：人工评审通过后，把优质 SQL、新踩坑写入 `05_历史/`、`04_踩坑/`；
3. **失效标记**：若某 chunk 在连续 N 次 run 中被召回但从未被采用，降级 `trust` 或下线（防止知识库只增不减）。

## 5. 支柱三：Skills

### 5.1 Skill 的判定标准

一个动作能成为 skill，必须同时满足四条，缺一条就不是 skill 而是 prompt：

| 标准 | 含义 | 反例 |
|---|---|---|
| **输入可判定** | 输入是结构化文件，符合 Schema | "帮我想想这个需求怎么建模" ✗ |
| **输出可判定** | 输出可被脚本校验对错 | "写一段优雅的 SQL" ✗ |
| **幂等/可重放** | 同输入同版本 → 同输出（或差异可解释） | "随机给三种方案" ✗ |
| **有校验器** | 附带 pass/fail 的检查脚本 | 只产出、不检查 ✗ |

正例：`生成 DWD DDL 并校验命名/分区/注释三件事`、`把回执事件流去重成漏斗宽表`。
反例：`设计整个电商域模型`——这是 agent 的判断工作，不是 skill。

### 5.2 Skill 清单（阶段 × 能力矩阵）

### 5.3 SKILL.md 规范

每个 skill 一个目录，一份说明，一份可执行校验器：

```
skills/sk-sql-ddl/
├── SKILL.md          # 人读的说明（front-matter + 正文）
├── schema/
│   ├── input.json    # 输入契约
│   └── output.json   # 输出契约
├── template/
│   └── hive_ddl.sql.j2
└── validate.py       # 返回 {"pass": bool, "violations": [...]}
```

```markdown
---
name: sk-sql-ddl
version: 1.2.0
stage: P5
engine: [hive, spark]
requires: [ontology, kb:naming, kb:sql_style]
inputs:  model_design.json, metric_spec.json
outputs: ddl/*.sql
gate:    G5
---

# 生成 Hive DDL

## 何时用
已通过 P3 建模与 P4 指标门禁，需要生成 ODS/DWD/DIM 层建表语句时。

## 输入约定
- `model_design.json` 中每张表必须带 `grain`、`layer`、`pii_level`
- 字段必须映射到本体 `attribute`，未映射字段一律拒绝生成

## 产出约定
- 全部表 `STORED AS ORC`，分区字段必须在末尾
- 每表每字段必须有 `COMMENT`
- 表注释必须包含：业务含义 + 粒度 + 更新频率

## 禁止事项
- 禁止无分区的明细表
- 禁止 `STRING` 存金额（必须 `DECIMAL(18,6)`）
- 禁止在 DDL 中写 `LOCATION` 硬编码路径（由平台注入）

## 失败处理
校验不通过时返回 violations 列表，不修改输入，由建模师修正后重跑。
```

### 5.4 示例：`SK-SQL-DML` 的校验规则集

DML 是最容易出错的一环，校验器必须比 LLM 更严：

| 规则 | 检查方式 | 严重级 |
|---|---|---|
| 语法可解析 | sqlglot `parse_one(dialect="hive")` | block |
| 分区必须过滤 | WHERE 中存在 `dt =` 或 `dt BETWEEN` | block |
| 除零保护 | 除法表达式分母含 `NULLIF` 或 `CASE WHEN ... >0` | block |
| 去重显式化 | 出现 `ROW_NUMBER` 且外层有 `= 1` | block |
| 禁止 SELECT * | 正则 + AST 双重检查 | block |
| 禁止笛卡尔积 | JOIN 必须带 ON | block |
| 幂等写入 | 必须是 `INSERT OVERWRITE ... PARTITION` | block |
| 动态分区配置 | 需要 `set hive.exec.dynamic.partition...` | warn |
| 小文件控制 | 需要 `distribute by` 或合并提示 | warn |
| 注释完整 | 关键 CTE 有 `--` 注释 | warn |
| 硬编码日期 | 必须用 `${bizdate}` 变量 | block |

> 这 11 条能挡住实际事故的绝大多数。它们都不是"风格问题"——`INSERT INTO` 不幂等导致重跑翻倍、除零导致整批任务失败、`SELECT *` 导致上游加字段后静默错位，都是生产事故级别。

## 6. 支柱四：Agents 与编排

### 6.1 角色定义

| 角色 | 职责 | 可写 | 只读 | 禁止 |
|---|---|---|---|---|
| **编排器** Orchestrator | 推进状态机、裁决门禁、装配上下文、记录指纹 | flow 状态 | 全部 | 写业务产物、改本体 |
| **需求分析师** | 把模糊需求拆成可计算指标 + 开放问题 | requirement.json | 本体（只读） | 定口径 |
| **取数分析师** Data Detective | 解析取数意图、定位数据、生成只读查询、产出结论与可信度 | `intent.json`, `analysis.json`, `query.sql` | 本体、知识库、ADS/DWS | 写本体、建表、执行 DDL/DML |
| **本体管理员** | 评审并合并 ontology_delta，唯一写本体者 | ontology/ | 全部 | 写 SQL |
| **建模师** | 总线矩阵、粒度、维度/事实表设计 | model_design.json | 本体、知识库 | 写 DDL/DML |
| **指标管理员** | 注册指标、消解口径冲突、维护指标手册 | metric_spec.json | 本体 | 改表结构 |
| **开发工程师** | 生成 DDL/DML | ddl/, dml/ | 上述全部 | 改本体/改指标口径 |
| **质量官** | 独立生成质量规则并执行 | dq_rules.json, dq_report | 全部 | 修改被测 SQL（防自证） |
| **审计官** | 抽样复查、评估豁免合理性 | audit_report | 全部 | 参与生产 |

**权责分离的三条硬约束：**
1. 写本体的人不写 SQL，写 SQL 的人不改口径；
2. 质量官不参与开发，规则必须独立生成；
3. 编排器不做业务判断，只做流程判断。

**跨泳道的一条硬约束：**
4. **A 线的产物不得直接进生产调度。** 取数 SQL 要上线必须走 B 线（经 P3 建模、P5 生成、G5 校验）。A 线只产出人的决策依据和生产线的**需求提案**，永不直连生产表。

### 6.2 状态机

```
                    ┌──────────── 回退边（带原因） ────────────┐
                    ▼                                          │
[P1 需求受理] ──▶ [P2 本体对齐] ──▶ [P3 维度建模] ──▶ [P4 指标定义]
   G1✅             G2✅              G3✅              G4✅
                                                          │
                                                          ▼
[P8 文档交付] ◀── [P7 血缘调度] ◀── [P6 质量规则] ◀── [P5 SQL 生成]
   G8✅             G7✅              G6✅              G5✅
     │
     └──▶ 归档 → 知识回流 → 结束
```

回退边不是异常处理，是**正常路径**：

| 门禁失败 | 典型原因 | 回退目标 |
|---|---|---|
| G1 | 需求里"渠道效果"没定义成功指标 | P1（补问） |
| G2 | 需要的维度本体里没有 | P2（补本体） |
| G3 | 粒度与既有事实表冲突 | P3（改粒度或复用） |
| G4 | 派生指标分子分母粒度不一致 | P4（重定义） |
| G5 | DML 除零未保护 | P5（自动重试一次，仍失败则回 P3） |
| G6 | 漏斗单调性不成立 | P3（大概率粒度错了） |
| G7 | 血缘出现环 | P3 |
| G8 | 字段无注释 | P5（补注释） |

**重试策略**：G5 自动重试上限 2 次（LLM 自修复），超过则升级为人工卡点；其余门禁一律不自动重试，直接回退到源头阶段——因为在错误输入上重试只会浪费 token。

**A 线状态机（独立、更短、更平）：**

```
[问题] ──▶ A1 意图 ──GA1──▶ A2 定位 ──▶ A3 查询 ──GA2──▶ A4 自检 ──GA3──▶ A5 结论 ──▶ A6 沉淀
              ▲                                              │
              └────────── 歧义回环（追问用户）                │
                                                             │
                         不可信回环（降级重查）◀──────────────┘
```

A 线没有 P2~P8 那种跨天回退，只有两个回环：**歧义回环**（A1 追问）和**不可信回环**（A4 降级重查）。任一回环超过 2 次就停下来问人，不无限重试。

### 6.3 门禁规则表

| 门禁 | 位置 | 校验内容 | 判定方式 | 失败动作 |
|---|---|---|---|---|
| **G1** 需求完整性 | P1 出口 | 每个"效果/转化"诉求都映射到可计算指标；开放问题清单为空或已人工确认 | 脚本 + 人工 | block → P1 |
| **G2** 本体一致性 | P2 出口 | O-01~O-10 全通过；所有引用对象存在；无 deprecated 引用 | 脚本 | block → P2 |
| **G3** 粒度唯一 | P3 出口 | 每个事实表粒度声明唯一；总线矩阵每个过程 ≥3 维度；无重复建表 | 脚本 | block → P3 |
| **G4** 指标合法性 | P4 出口 | 分子分母同粒度同时间窗；修饰词已注册；caliber ≥20 字；无同义指标 | 脚本 | block → P4 |
| **G5** SQL 合规 | P5 出口 | §5.4 的 11 条规则全通过 | sqlglot AST + 规则 | 自动重试 2 次 → 人工 |
| **G6** 质量达标 | P6 出口 | 核心字段规则覆盖率 ≥90%；空跑通过；无 block 级违规 | 脚本 | block → P3 |
| **G7** 血缘完整 | P7 出口 | 无环；无孤立节点；上游均可用；调度时序合法 | 图算法 | block → P3 |
| **G8** 文档完备 | P8 出口 | 字段注释覆盖 100%；指标 caliber 覆盖 100%；有 owner | 脚本 | block → P5 |

> A 线的 GA1~GA3 不并入本表：两套门禁强度差 3 倍，混在一起看会让人误以为取数也要过 8 关。A 线门禁见 §7.1。

### 6.4 HITL 人工卡点

只有三个卡点，多了就没人用：

| 卡点 | 时机 | 人工要看什么 | 不允许跳过 |
|---|---|---|---|
| **H1 口径确认** | P4 出口，G4 前 | 每个新增/变更指标的口径文字，特别是分子分母 | ✅ |
| **H2 建表评审** | P3 出口，G3 前 | 是否新建表（复用优先）、粒度是否与既有冲突 | ✅ |
| **H3 上线放行** | P7 出口，G7 后 | 血缘、调度时间、资源评估、回滚方案 | ✅ |

**豁免机制**：任何 block 级门禁可被人工豁免，但必须写入 `waivers.json`（谁、何时、为什么、有效期），且审计官每月复盘豁免清单。**豁免必须留痕，否则门禁形同虚设。**

### 6.5 产物指纹（可重放）

每次 run 记录：

```json
{
  "run_id": "profile-20261122-02",
  "fingerprint": {
    "ontology": "v1.4.0",
    "knowledge": "kb-snapshot-2026-11-15",
    "skills": { "sk-sql-ddl": "1.2.0", "sk-sql-dml": "1.5.1" },
    "model": "claude-x@2026-11",
    "flow": "v0.1"
  },
  "gates": { "G1": "pass", "G2": "pass", "...": "..." },
  "waivers": []

```

四元组一致 → 产物可复现。这是把"LLM 输出不可控"变成"工程可管理"的关键一步：**不追求确定性，追求可追溯性**。

## 7. 两条流水线：取数分析 / 数仓开发

### 7.0 全景：一套底座，两条泳道

```
                          ┌─────────────────────────────────────┐
                          │           共享底座（约 80%）          │
                          │  本体 ontology │ 知识库 knowledge     │
                          │  SQL 校验规则 │ 契约 Schema │ 指纹    │
                          └──────────────┬──────────────────────┘
                        ┌────────────────┴────────────────┐
                        ▼                                 ▼
          A 线：取数分析（分钟级）              B 线：数仓开发（天~周级）
          A1 意图解析  ─ 歧义先暴露              B1 需求受理
          A2 找数定位  ─ ADS>DWS>DWD>ODS        B2 本体对齐
          A3 查询生成  ─ 只读五护栏              B3 维度建模
          A4 结果自检  ─ 五项 + 可信度           B4 指标定义
          A5 结论生成  ─ 只描述事实              B5 SQL 生成
          A6 沉淀/晋升 ──────┐                  B6 质量规则
             GA1~GA3         │                  B7 血缘调度
                             │                  B8 文档交付
                             │                     G1~G8
                             │                       │
                             ▼                       ▼
                    指标化提案 ──▶ 进本体 ──▶ A 线可检索（闭环）
```

**两线复用关系（这张表回答了"四支柱怎么同时服务两个场景"）：**

| 能力 | A 线（取数） | B 线（开发） | 说明 |
|---|---|---|---|
| 本体 | 只读，高频查询 | 读写，低频变更 | 同一份 |
| 知识库 | 全量 | 全量 | 同一份 |
| SQL 校验 | 子集（安全类 5 条） | 全集（11 条） | A 线不需要幂等/动态分区 |
| 指标定义 | 复用，不改 | 定义与注册 | A 线想创新指标 → 走晋升 |
| 血缘 | 只读使用（找数） | 生成与维护 | |
| 质量 | 结果自检（轻） | 表级规则（重） | |
| 门禁 | GA1~GA3 | G1~G8 | 强度差 3 倍 |

> 一个反直觉的结论：**A 线不是 B 线的简化版。** A 线的难点是「歧义消解 + 可信度自证」（我算的这个数凭什么可信），B 线的难点是「结构正确 + 可重跑」。用 B 线的重型门禁套 A 线，分析人员会直接绕开工具回去手写 SQL；用 A 线的轻门禁套 B 线，等于没有门禁。

### 7.1 A 线：取数分析流水线（A1~A6）

**目标**：分析人员问一句话，60 秒内拿到「能跑、能对、能解释」的结果，而不是一段"看起来对"的 SQL。

#### A1 意图解析：先暴露歧义，再动手

**动作**：
1. 判定意图类型：`lookup`（查数）/ `trend`（趋势）/ `attribution`（归因）/ `comparison`（对比）/ `cohort`（分群）；
2. 抽取五要素：指标、维度、时间窗、过滤、对比基线；
3. **歧义必须显式列出**，不许静默消解。

**产出** `intent.json`：

```json
{
  "question": "上周各渠道 GMV 为什么比前一周少了 3%？",
  "intent_type": "attribution",
  "target_metrics": [
    { "ref": "GMV", "caliber": "支付成功金额，按 pay_time 归日，退款不回冲", "confidence": 0.95 }
  ],
  "filters": ["CHANNEL_ALL"],
  "time_range": { "start": "2026-11-09", "end": "2026-11-15", "grain": "1d" },
  "compare_base": "2026-11-02 ~ 2026-11-08",
  "suggested_dimensions": ["channel_name", "category_l1", "shop_type"],
  "ambiguity": [
    {
      "item": "GMV 归日口径",
      "options": ["按 pay_time 归日（主口径）", "按 create_time 归日（下单口径）"],
      "default": "主口径",
      "action": "按主口径执行，并在结论中标注所用口径"
    }
  ],
  "unresolvable": []
}
```

**GA1 门禁**：`unresolvable` 为空；`ambiguity` 中每项必须有 `default` + `action`。**不允许"猜一个口径然后不说"。**

#### A2 找数定位：ADS > DWS > DWD > ODS

**动作**：
1. 指标 → 本体 → 落地表与字段（`metric.fact_table` + `metric.ads_field`）；
2. 指标不存在时按序降级：① 找同义指标 → ② 用原子指标现算 → ③ 从 DWD 现算（**必须标注"非标准口径"**）；
3. 产出**取数路径卡**：用哪张表、哪个字段、扫描哪段分区、预估扫描量、要不要 JOIN。

```json
{
  "chosen": "ads.ads_trade_metric_1d",
  "path": [
    { "metric": "GMV",       "table": "ads.ads_trade_metric_1d", "field": "gmv" },
    { "metric": "ORDER_CNT", "table": "ads.ads_trade_metric_1d", "field": "order_cnt" }
  ],
  "partition_range": "dt in ['2026-11-02','2026-11-15']",
  "scan_estimate_gb": 0.6,
  "degradation": null,
  "warnings": ["category_l1 维度在 ADS 层不存在，需下钻 dws_item_sale_1d"]
}
```

**硬规则：能查现成的绝不碰明细。** ADS 缺维度时，先提示"该维度在 ADS 不存在"，再降级到 DWS，并写明降级原因。

#### A3 查询生成：只读 + 五道硬护栏

护栏在**语法层强制**，不靠提示词：

| # | 护栏 | 规则 | 拦的是什么 |
|---|---|---|---|
| 1 | 只读 | 只允许 `SELECT` / `WITH`，出现 DDL/DML 直接拒绝 | 误伤生产表 |
| 2 | 分区必填 | 必须有 `dt` 过滤，范围 ≤90 天 | 全表扫拖垮集群 |
| 3 | 行数上限 | 探索期自动加 `LIMIT 2000`；导出需审批 | 拉爆客户端 |
| 4 | 列裁剪 | 禁止 `SELECT *` | 同上 |
| 5 | JOIN 上限 | ≤3 表，超过要求拆步骤 | 可读性与性能 |

产出 SQL + **口径说明**（给非技术读者看：这段数是怎么算出来的）。

```sql
-- 问题：上周各渠道 GMV 为什么跌了 3%？
-- 指标：GMV（主口径：支付成功金额，按 pay_time 归日，退款不回冲）
-- 注意：客单价必须 SUM/SUM，不能对日客单价求平均
SELECT
  p.dt,
  c.channel_name,
  SUM(p.pay_amt)                                                     AS gmv,
  COUNT(DISTINCT p.order_id)                                         AS order_cnt,
  ROUND(SUM(p.pay_amt) / NULLIF(COUNT(DISTINCT p.order_id), 0), 2)   AS aov
FROM dwd.dwd_pay_flow_di p
LEFT JOIN dim.dim_channel_df c
  ON p.channel_code = c.channel_code
 AND c.dt = '${dt}'
WHERE p.dt BETWEEN '2026-11-09' AND '2026-11-15'   -- 强制分区过滤
GROUP BY p.dt, c.channel_name
LIMIT 2000;                                        -- 强制行数上限
```

**A 线最高频的四类错误（必须进知识库当范例）：**

| 反例 | 为什么错 | 正例 |
|---|---|---|
| `AVG(aov_1d)` | 客单价的平均 ≠ 总 GMV/总订单数；小渠道权重被放大，典型辛普森悖论 | `SUM(pay_amt)/SUM(order_cnt)` |
| `WHERE dt = '上周'` | Hive 无此写法，且分区条件失效导致全表扫 | `dt BETWEEN … AND …` |
| 无等值条件的 JOIN | 笛卡尔积，行数爆炸（渠道维表未限 dt 会扇出） | 必须带等值 ON 且维表带分区 |
| 用 `COUNT(1)` 当订单数 | 一笔订单多笔支付流水会被重复计数 | `COUNT(DISTINCT order_id)` |

#### A4 结果自检：先证明可信，再给结论

跑完不直接出结论，先过五项检查：

| 检查 | 方法 | 不通过时 |
|---|---|---|
| 总量对账 | 与 `ads_trade_metric_1d` 同周期总量比对，差异 >5% | 标差异 + 给可能原因 |
| 维度完备 | 分维度求和 = 总量 | 标"存在维度缺失/其它" |
| 样本量 | 分母 <1000 的分组 | 标"样本不足，不可下结论" |
| 突变 | 环比变化 >50% | 先确认是否数据问题 |
| 空值 | 关键字段空值率 | 单列展示，不静默丢弃 |

**产出** `analysis.json`，带**可信度标签** `high` / `medium` / `low`。`low` 必须在结论正文里显式说明原因。

#### A5 结论生成：只描述事实，归因给验证路径

输出结构固定五段：

1. **一句话结论**（可含数字，不含因果断言）
2. **支撑数据**（≤5 行表格）
3. **归因假设**（按贡献度排序，每条附一条"验证查询"）
4. **不确定性说明**（口径 / 样本 / 数据延迟）
5. **下一步建议**

> 硬规则：**不允许说"因为 A 所以 B"**，只能说"A 与 B 同向变化，可用这条 SQL 验证"。这是分析工具与算命的分界线。

#### A6 沉淀与晋升

三件事：查询模板入库（`knowledge/03_范例/queries/`）、口径说明归档、晋升评估。

**晋升机制 —— 两条线的连接点（本设计最看重的一条）：**

| 触发条件 | 动作 | 去向 |
|---|---|---|
| 同一 `intent` 30 天内被 ≥3 人问过 | 生成「指标化提案」 | B 线 P4 |
| 同一 SQL 模板被复用 ≥5 次 | 提升为知识库范例 | `knowledge/03_范例/` |
| 指标已在 ADS 但被反复现算 | 说明 ADS 缺维度 | B 线 P3（加维度） |
| 某口径被业务写进考核 | 强制晋升 + H1 口径确认 | B 线 P2 / P4 |

> 没有这条通道，A 线的价值止于"这次算对了"，永远不会变成组织能力。**分析人员是需求的发现者，开发是需求的固化者。**

**A 线门禁汇总：**

| 门禁 | 位置 | 校验 | 失败动作 |
|---|---|---|---|
| **GA1** 口径明确 | A1 出口 | 歧义已标注、无不可解项、五要素齐备 | 追问用户 |
| **GA2** SQL 安全 | A3 出口 | 只读 / 分区 / LIMIT / 无 `SELECT *` / JOIN≤3 | 自动修复一次，仍失败则拒绝 |
| **GA3** 结果可信 | A4 出口 | 五项自检通过，或已标注 `low` 及原因 | 降级 + 强制说明 |

- 每阶段产物落 `runs/<run_id>/P<n>_<name>/`，只增不改（改则新建版本目录）；
- 每阶段开头由编排器装配上下文（本体切片 + 知识检索结果 + 上游契约），装配清单写入 `context_manifest.json`；
- 每阶段结束必须产出 `gate_report.json`（pass / fail + violations 列表）。

---

#### P1 需求受理：把"效果变好"变成可计算

**输入**：需求原文（IM 聊天、文档、邮件均可）、业务方信息、期望上线时间。

**动作**：
1. 抽取**业务目标**（要决策什么）与**验收诉求**（看什么数）；
2. 拆成「可计算」与「不可计算」两部分，不可计算部分列入 `open_questions`；
3. 识别涉及的**对象**与**过程**，映射到本体已有 ID（找不到就标记 `unmapped`，交给 P2）；
4. 识别**时间范围、维度切片、对比基线**。

**产出契约**（`requirement.json` 节选，完整 Schema 见 §8.2）：

```json
{
  "run_id": "channel-gmv-20261122-01",
  "title": "渠道 GMV 日报与会话归因",
  "requester": "trade-ops",
  "business_goal": "定位各渠道 GMV 下滑的环节与品类",
  "objects": ["USER", "PRODUCT", "ORDER", "SHOP", "CHANNEL"],
  "processes": ["ORDER_CREATE", "PAY", "REFUND"],
  "metrics_requested": [
    { "name": "GMV / 订单数 / 支付人数", "type": "volume" },
    { "name": "客单价、退款率、支付转化率", "type": "ratio" }
  ],
  "dimensions_required": ["日期", "渠道", "一级类目", "店铺类型"],
  "time_grain": "1d",
  "comparison": ["环比", "同比"],
  "open_questions": [
    "GMV 按 pay_time 还是 create_time 归日？退款是否回冲当日 GMV？",
    "一笔订单多笔支付流水（部分支付/补差价）算一笔还是多笔？",
    "渠道归属以支付流水上的 channel_code 为准，还是以下单时的来源渠道为准？"
  ],
  "unmapped": ["店铺类型（自营/三方/POP）— 本体暂无该属性"]
}
```

**G1 门禁**：`open_questions` 必须为空或已人工答复；`unmapped` 非空则必须进入 P2。

> 这里刻意**不**直接产出 SQL 或模型。需求阶段的产出越"像最终答案"，后面越难纠错。

---

#### P2 本体对齐：先改事实源，再动表

**输入**：`requirement.json`、现有本体切片。

**动作**：
1. 对 `unmapped` 项生成 `ontology_delta`（新增对象/属性/过程/指标提案）；
2. 与既有本体做同义冲突检测（"GMV"是否已有定义）；
3. 每个 delta 必须附**影响面**（哪些已有表/指标会受影响）。

**产出**：`ontology_delta/ecommerce_v1.2.0.yaml`（提案，未合并）+ `impact_analysis.md`。

**G2 门禁**：O-01~O-10 全通过；影响面必须评估；`deprecated` 节点不得被引用。

**关键约束**：本体管理员 agent 是唯一能合并 delta 的角色，且合并必须走 git PR。**任何绕过本体的建模，在 P3 都会被 G3 拦下**（因为 model_design 里每个字段必须映射到本体 attribute ID）。

---

#### P3 维度建模：总线矩阵 + 粒度声明

**输入**：`requirement.json`、合并后的本体、历史总线矩阵。

**动作**：
1. 确认业务过程（不得随意新增，优先复用）；
2. 声明每个事实表的**粒度**（`grain`），粒度必须唯一且不与既有事实表重叠；
3. 选择**一致性维度**，更新总线矩阵；
4. 定义 `SCD` 策略（商品类目、店铺属性用 type1，用户等级与收货地址用 type2）；
5. 复用优先：能在已有 DWS 上加维度就绝不新建表。

**产出**：`model_design.json`（含 `tables[]`，每张表带 `layer` / `grain` / `dimensions` / `measures` / `source_tables` / `pii_level` / `partition`）。

**G3 门禁**：
- 每个事实表有且仅有一个 `grain`；
- 不同事实表不得有相同 `grain`（除非明确是聚合层级差异）；
- 总线矩阵每个业务过程至少关联 3 个维度；
- 新建表必须写明"为什么不复用现有表"。

**H2 人工卡点**：建表评审。数仓最贵的成本是表数量，这一关不放自动通过。

---

#### P4 指标定义：原子 → 派生，口径一次说清

**输入**：`model_design.json`、本体已有指标。

**动作**：
1. **先查后建**：先在既有指标里检索同义/近似指标，能复用则复用；
2. 定义原子指标（业务过程 + 度量 + 聚合方式）；
3. 定义派生指标（原子指标 + 修饰词 + 时间周期），**强制写分子分母**；
4. 写 `caliber` 口径文字（≥20 字，必须包含去重规则、空值处理、边界情况）；
5. 冲突裁决：同一业务概念出现多个口径时，必须选出主口径，其余标记为 `secondary` 并写 `forbidden_as`。

**产出**：`metric_spec.json`（含 `atomic[]`、`derived[]`、`conflicts_resolved[]`）。

**G4 门禁**（脚本可全自动）：
- 派生指标分子分母**粒度相同、时间窗相同**；
- 修饰词全部在本体修饰词字典中；
- 无同义指标（`(process, modifiers, time_window)` 维度下语义重复）；
- 每个指标有 `caliber`、`owner`、`coverage`；
- `forbidden_as` 与 `caliber` 不矛盾。

**H1 人工卡点**：口径确认。这是全流程**唯一必须人工签字**的业务决策点。

---

#### P5 SQL 生成：方言 + 规范 + 可解析

**输入**：`model_design.json`、`metric_spec.json`、知识库（`sql_style.md` + `hive_functions.md` + 范例）。

**动作**：
1. DDL：建表语句，字段类型、注释、分区、存储格式全部就位；
2. DML：按分层顺序生成，每层一个文件，顶部写目标表 / 粒度 / 上游表 / 负责人；
3. 自检：跑 `SK-SQL-REVIEW`，命中规则则自动修一次再提交。

**G5 门禁**：§5.4 的 11 条规则全通过（sqlglot 解析 + 规则集）。自动重试上限 2 次。

**反例 vs 正例（电商域最典型的三处）：**

| 场景 | 反例 | 为什么错 | 正例 |
|---|---|---|---|
| 比率计算 | `SUM(aov_daily) / COUNT(1)` | 分母是"有数据的天数/渠道数"，不是订单数；小渠道权重被放大 | `SUM(pay_amt) / NULLIF(SUM(order_cnt), 0)` |
| 支付流水去重 | 直接 `LEFT JOIN 支付流水` | 一笔订单多笔流水（部分支付、补差价）导致 GMV 翻倍 | 先 `ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY pay_time DESC)` 取 rn=1 |
| 重跑 | `INSERT INTO` | 重跑一次数据翻倍，无法回溯 | `INSERT OVERWRITE TABLE ... PARTITION (dt=...)` |

**输入**：`model_design.json`、`metric_spec.json`、`ddl/`、`04_踩坑/`。

**动作**：**质量官独立生成**（不看 DML 实现，只看契约，避免"照着自己的实现写规则"）。

规则六类：

| 类型 | 电商域示例 | 严重级 |
|---|---|---|
| 唯一性 | `(order_id, sku_id)` 在 `dwd_order_item_di` 唯一，重复率 < 0.1% | block |

| 时效 | T+1 08:00 前产出 | warn |

**G6 门禁**：核心字段覆盖率 ≥90%；空跑（`WHERE dt='${bizdate}' AND 1=0` 的语法与权限校验）通过；无 block 级违规。

## 9. 样板走查：电商交易域端到端

> 本章是全篇的"可执行锚点"。前面所有抽象规则，在这一章都有对应的具体产物；而且这些产物在仓库里**真实存在**，路径写在每一节开头。评审时建议先看本章，再回看规则。
>
> 样板域选择：**电商交易**（用户 / 商品 / 下单 / 支付 / 退款 / 渠道）。它比推送简单，但该有的口子都在——同一笔订单有定金与尾款、退款要不要回冲、渠道表会不会扇出、客单价能不能"平均的平均"。这些正是门禁要卡的地方。

### 9.0 领域速写：电商交易数据长什么样

```text
浏览 ──▶ 下单 ──▶ 支付 ──▶ 发货 ──▶ 收货 ──▶ 退款
view    order    pay      ship     receive   refund
         │        │
         │        └─ 一笔订单可多次支付（定金 + 尾款），去重键不是 order_id
         └─ 应付金额与实付金额不是一回事，GMV 只认实付
```

数据源清单（本体的输入侧，每个都要确认可获取性与口径）：

| 数据源 | 内容 | 时效 | 典型问题 |
|---|---|---|---|
| 订单主表 | 订单、用户、商品、应付金额、状态 | T+0 | 状态机回退（已支付→已取消） |
| 支付流水 | 每笔支付/退款的金额与时间 | T+0 | **一单多笔**（定金+尾款）、支付流水号可能为空 |
| 退款单 | 退款金额、退款时间、原因 | T+1 | 部分退款、跨月退款 |
| 用户表（快照日表） | 注册信息、生日、性别、注册地 | T+1 | 生日缺失、城市等级是注册地不是收货地 |
| 商品维表 | SKU、类目、店铺 | T+1 | 类目调整会改历史归属 |
| 渠道维表 | 渠道编码、渠道名 | T+1 | **编码与名称一对多**，直接 JOIN 会扇出 |

**三个必须先定死的口径分歧点**（不定就会在 SQL 里各写各的）：

| 分歧 | 两种常见写法 | 本文定稿 | 理由 |
|---|---|---|---|
| GMV 归日 | 按 `create_time` / 按 `pay_time` | **按 `pay_time`** | 下单未付不是成交；跨日支付的订单归到支付那天 |
| GMV 是否回冲退款 | 回冲 / 不回冲 | **不回冲**，退款单看 `REFUND_RATE` | 回冲会让"昨天的 GMV"随时间变小，下游无法解释 |
| 客单价能不能二次平均 | `AVG(日客单价)` / `SUM(GMV)/SUM(订单数)` | **后者**，`AOV` 标 `non_additive` | 日均值再平均等于给每天相同权重，月初月末订单量不同就会偏 |

> 这张表就是本体要承载的东西。LLM 靠常识永远猜不到"你们的 GMV 回不回冲"——它只能猜一个看起来合理的。

## 10. 风险与坑

### 10.1 电商交易域专属（9 条，全部已进本体、质量规则或待办）

1. **一单多笔支付**：定金 + 尾款是两笔流水，`COUNT(DISTINCT order_id)` 才是订单数，`COUNT(1)` 会把一单算成两单。
2. **退款不回冲**：如果 GMV 随退款回冲，上周的日报会随时间变小，业务无法解释。退款用 `REFUND_RATE` 单独看。
3. **渠道维表扇出**：`channel_code` 在维表里可能对应多行（改名、多平台），直接 JOIN 会让"一个 dt + 一个渠道只有一行"失效——必须先聚合再 JOIN，或确认键唯一。
4. **客单价不可二次平均**：日客单价是 `non_additive`，`AVG(日客单价)` ≠ `SUM(GMV)/SUM(订单数)`。
5. **城市等级是注册地不是收货地**：`dim_user_df.city_level` 来自注册信息；要按收货地分析必须接入地址表（待办 T-20261128-02）。
6. **生日边界**：年龄段按周岁算，"生日当天进新档"；缺生日写 `UNKNOWN` 而不是推断。
7. **测试账号**：只按 `is_test = 0` 过滤，不要用 `user_id NOT LIKE 'test\_%'`（后者既漏又依赖命名习惯）。
8. **档位写死多处**：同一套分桶会同时出现在 SQL CASE、DQ 枚举、DQ 序号映射、字典表四个地方，改一处必挂——根治方案是收敛到 `dim_tag_df`（待办 T-20261128-03）。
9. **时间窗不含当天**：`[dt-N, dt-1]`，当天数据不全，含当天会让"近30天"在一天之内反复抖动。

### 10.2 A 线（取数分析）专属（6 条）

| # | 坑 | 后果 | 处置 |
|---|---|---|---|
| 1 | **对比率求平均** | 结论方向性错误（辛普森悖论），是最隐蔽也最致命的一类 | `SK-QRY-VERIFY` 检测 `AVG(*_rate)` 直接 block |
| 2 | **全表扫** | 一个查询拖垮整个集群，影响所有下游任务 | 分区必填 + ≤90 天 + 扫描量预估拦截 |
| 3 | **口径自创** | 与看板"两个真相"，对数会永远开不完 | 指标只能从本体取；现算必须标"非标准口径" |
| 4 | **小样本下结论** | 3 条记录算出 0% 支付转化率，被当成重大发现 | 分母 <1000 强制标注"样本不足" |
| 5 | **相关当因果** | "因为改了大促文案所以 GMV 涨"，误导决策 | 禁止因果断言，只给验证查询 |
| 6 | **取数散落** | 同一问题 5 个人 5 份 SQL，结果还都不一样 | A6 沉淀 + 晋升机制（§7.1） |

> 第 1 条要特别强调：`AVG(rate)` 在数仓里几乎从不是你想算的东西。它把每个分组的权重拉成相同，而真实业务里 3 条记录的任务和 30 万条记录的任务权重差了五个数量级。这类错误**跑得通、看着对、结论错**，只能靠门禁拦。

### 10.3 工作流通用（5 条）

| # | 风险 | 表现 | 缓解 |
|---|---|---|---|
| 1 | LLM 幻觉造字段 | 引用本体不存在的属性 | 字段必须映射本体 ID，未映射硬失败（P3 门禁） |
| 2 | 契约过严导致不可用 | 每个需求都被门禁拦住 | 分级严重性（block/warn），warn 不阻断；豁免留痕 |
| 3 | 知识库陈旧 | 召回旧语法/旧口径 | 快照 + `trust` 分级 + 未采用降级 |
| 4 | 门禁被豁免架空 | 豁免常态化 | 审计官月度复盘豁免清单，超阈值暴露 |
| 5 | 无法重放 | 出问题查不到当时上下文 | 四元组指纹 + `context_manifest.json` 全量记录 |

### 10.4 本设计尚未解决的问题（诚实列出）

1. **商品类目变更的历史归属**：类目调整后，历史 GMV 是按"下单时类目"还是"当前类目"统计，本体尚未强制；
2. **退款跨月归属**：退款可能发生在支付次月，回冲规则（回冲支付日 or 退款日）需要业务定，方案只给了默认；
3. **跨店铺同名 SKU 去重**：`product_id` 只在店铺内唯一，跨店铺合并口径需 `(shop_id, sku_id)`，与画像标签的"偏好品类"互相影响；
4. **实时成交看板**：本方案只覆盖 T+1，实时 GMV 需 Flink 链路，属 M5。
