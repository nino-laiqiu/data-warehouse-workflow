# SKILL: sk-req-validate — 翻译稿可开工校验（G1）

## 这是什么

检查 `requirements/需求分析员/<需求目录>/REQ-*.md` 是否满足"两个开发者可以独立开工且不会理解分歧"。

**不是**什么：不翻译需求、不改文档、不评判需求价值。它只做一件事——**把"还能不能往下走"变成一个可以用脚本回答的问题**。

## 为什么这条门禁比看起来重要

P2 是双轨开发，成本 ×2。一旦带着歧义进 P2，两条轨会各自脑补一种理解，P3 比对时才暴露，返工成本是双份的。

所以 G1 的判定标准很硬：**「待确认项」不为空就不许开工**。宁可停下来问一句，也不要两个人一起猜。

## 输入

```bash
python skills/sk-req-validate/validate.py --doc requirements/需求分析员/渠道GMV日报需求20261122/REQ-20261122-01.md
```

可选 `--registry` 指定登记簿（默认 `requirements/反馈者/_registry.jsonl`）。

## 检查六件事

| # | 检查 | 失败意味着 |
|---|---|---|
| 1 | 8 段齐全且顺序正确 | 上游漏写了某一块 |
| 2 | 「待确认项」为空 | 还有歧义没消，不许进 P2 |
| 3 | 引用了原始需求编号与其 `sha256`，且与登记簿一致 | 翻译稿可能基于旧版原件 |
| 4 | `ontology/…yaml` 引用都能找到文件 | 引用了一个不存在的口径 |
| 5 | 反引号里的本体 id（如 `GMV`）在 ontology 里真实定义 | 编造了口径 |
| 6 | 验收标准含数字与比较符 | "数据要准确"不是验收标准，是许愿 |

第 4、5 条是防幻觉的关键：翻译者最容易做的事，就是写一个听起来很合理、但本体里根本不存在的指标名。

## 输出

```json
{"ok": false, "errors": ["第 8 段「待确认项」不为空：「渠道」是否含小程序分销渠道，需确认"], "sections": 8}
```

## 失败时怎么办

- 缺段 / 待确认项非空 → 退回 `requirement-translator` 补齐。
- 引用的本体 id 不存在 → 要么改引用，要么提 `ontology_delta`。**不许在文档里临时定义一个口径**。
- sha256 对不上 → 原件被改过或翻译稿基于旧版，停下来问人。
