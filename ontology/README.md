# ontology/ —— 唯一事实源

只回答一个问题：**这个指标/这个对象/这个过程是什么**。

不回答：这 SQL 怎么写（`knowledge/`）、这活谁干（`agents/`）。

## 为什么是事实源

同一个"到达率"，分析师算 78%、开发算 92%，根因不是谁算错了，而是口径散落在三处：埋在 SQL 里、写在 wiki 里、留在某人的聊天记录里。本体把口径收敛到**一个可校验的文件**，其他所有地方都只能引用。

## 结构

| 目录 | 放什么 | 关键字段 |
|---|---|---|
| `schema/` | 元模型与校验器 | `meta-model.yaml`、`validate.py` |
| `dict/` | 枚举字典 | 平台、渠道、修饰词 |
| `object/` | 对象（维度来源） | 设备、用户、任务、模板 |
| `process/` | 业务过程 | 圈选、下发、转化 |
| `metric/atomic/` | 原子指标 | 单个过程上的可加度量 |
| `metric/derived/` | 派生指标 | 原子指标 + 修饰词 + 时间窗口 |
| `link/` | 关系 | 对象之间的关联与基数 |
| `constraint/` | 约束 | 业务不变量（漏斗单调、口径互斥） |

## 写权限

**只有本体管理员能写**，且只能通过 `ontology_delta` 提案 → git PR 合并。其余角色一律只读。

这不是防人，是防漂移：如果模型师能直接改本体，"口径"就会变成每次建模的即兴决定。

## 可校验性

本体必须在**没有 LLM** 的情况下可读、可校验：

```bash
python ontology/schema/validate.py
```

校验内容：字段齐全、ID 命名合规、引用的对象存在、指标能追到过程、约束无矛盾。CI 里跑这一条，可以挡住 90% 的本体腐化。
