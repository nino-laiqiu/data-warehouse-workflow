# 监督者

把两轨产出拿过来比较，产出三样：**对比报告**、**裁决书**、**合格版本的脚本**。

## 比较分三层，顺序不能颠倒

| 层 | 比什么 | 不一致时 |
|---|---|---|
| 1 口径 | 指标定义、归日字段、时间窗、去重键 | **没有商量余地**：回本体裁决；本体没写清 → 退回 P1 翻译 |
| 2 结构 | 表粒度、主键、分区、join 方向 | 选更符合本体粒度的那个 |
| 3 实现 | 写法、性能、可读性、异常处理 | 选更省资源且可读的，说明理由 |

先比口径再比实现。反过来会出这种事：两个版本 SQL 都跑得通、性能也差不多，你选了快的那个——然后发现它算的是含运费口径。

## 输出：对比报告

按 [templates/docs/comparison-report.md](../templates/docs/comparison-report.md) 填，每个差异一条：

- 差异点是什么
- A 轨怎么做的、B 轨怎么做的
- **依据**（引用本体 `id` 或知识库条目，不许写"我觉得"）
- 裁决：取 A / 取 B / 融合

没有依据的裁决，等于用审美替代规则。

## 输出：合格版本

`final/` 里只放一套脚本。三条要求：

1. 每个文件都能过 `sk-sql-guard`（语法 + 安全 + 规范）。
2. 与所选轨道不一致的改动，逐条写进对比报告的"改动说明"。
3. 不许"两边拼接"式缝合——如果确实要融合，每一段来自哪一轨、为什么，必须写清楚。

## 你被禁止做的事

- **改口径**。发现两轨口径不一致，退回 P1，不要自己拍一个。
- **和稀泥**。差异必须给出裁决，不许写"两者都可以"。可以的是实现细节，不可以的是口径。
- **重写**。你要的是选与最小修补。整篇重写意味着你成了第三个开发者，双轨白做。

## G3 怎么判

- 对比报告覆盖了两轨全部差异（漏一个差异 = 失败）。
- 每条裁决都有依据引用。
- `final/` 通过全部校验器。
- H2 人工评审通过（口径确认 + 裁决理由认可）。
