# 05 取数路径（先选表，再写 SQL）

## 第一步：判断问题属于哪一类

| 问题长什么样 | 起点 | 为什么 |
|---|---|---|
| "昨天 GMV 多少"、"这个月各渠道成交" | `ads_trade_metric_1d` | 现成的指标宽表，比率列齐 |
| "某类目/某店铺 卖得怎么样" | `ads_trade_metric_1d` → 不够再下探 `dws_item_sale_1d` | 宽表按渠道×店铺，类目维要自己 join |
| "某商品/某 SKU 的销量" | `dws_item_sale_1d` | 天×SKU 粒度，最细的汇总 |
| "某个用户的消费情况" | `dws_trade_user_1d` | 天×用户粒度 |
| "转化率/漏斗/加购率" | `ads_trade_funnel_1d` | 漏斗必须同人同窗口，别自己拼 |
| "订单明细/退款明细/某笔支付" | `dwd_order_main_di` / `dwd_refund_di` / `dwd_pay_flow_di` | 只有明细层才有单笔粒度 |
| "用户画像/商品属性" | `dim_user_df` / `dim_product_df` | 维表 |
| "去年同期/上个月" | `ads_trade_metric_1d` 的 `_yoy` / `_mom` 列 | 别自己写窗口，口径容易跑偏 |

## 第二步：先 ADS，再逐层下探

```
ads_*  →  dws_*  →  dwd_*  →  ods_*（基本不用，除非查数据源问题）
```

下探只在三种情况下发生：
1. **ADS 没有你要的维度组合**（比如要"类目 × 渠道"，宽表只有"店铺 × 渠道"）。
2. **ADS 的口径不满足需求**（比如要"含运费口径的 GMV"）。
3. **要验证 ADS 的数对不对**（用明细重算一遍，这是最应该做的下探）。

**不要**因为"直接查明细更灵活"就跳过汇总层：明细层单日动辄上亿行，一个不小心就是几十分钟的查询和一笔不小的账单。

## 第三步：写 SQL 前的四个确认

1. **时间字段**：是 `pay_time` 还是 `create_time`？GMV 按 `pay_time`，下单量按 `create_time`，混用是本项目最常见的一号错误。
2. **分区范围**：必须写 `dt BETWEEN ... AND ...`，且跨度 ≤ 90 天（A 线硬门禁 GA2）。
3. **去重键**：支付按 `(order_id, pay_seq)`，行为按 `event_id`，不先去重就 `COUNT` 必虚高。
4. **比率**：要比率就回到分子分母，`AVG(rate)` 一律不许。

## 四个常见问题的完整路径

**Q1：昨天各渠道 GMV 和客单价**
→ `ads_trade_metric_1d`，`dt='2026-11-21' AND channel_id<>'ALL'`，`SUM(gmv)`、`SUM(gmv)/SUM(order_cnt)`。
注意：客单价必须重算，不能 `AVG(aov)`。

**Q2：11 月新客的复购率**
→ `dws_trade_user_1d` 筛 `is_new_user=1` 的首购月份，再数这些人里 11 月支付 ≥2 天的比例。
注意：复购的"次"按天算还是按订单算要写清楚，两种结果差很多。

**Q3：某类目 618 当天 Top10 商品**
→ `dws_item_sale_1d` + `dim_product_df`（带 `dt`），按 `cate_l1_id` 过滤，`SUM(sale_amt)` 排序取 10。
注意：`dim_product_df` 的 `dt` 必须是 618 当天，否则类目归属可能已经变了。

**Q4：为什么昨日 GMV 环比跌了 20%**
→ 先 `ads_trade_metric_1d` 拆渠道，再 `ads_trade_funnel_1d` 看哪一步掉了，最后才下探明细。
注意：这一步容易变成"编故事"。没有数据支撑的因果解释不能写，只能写"渠道 A 掉了 30%，占比 12%，可解释 3.6pct"。

## 什么时候该停下来问人

- 问题里出现**没定义过的词**（"活跃用户""有效订单""高价值客户"）——回本体查，查不到就提 `ontology_delta`，不要自己下定义。
- 需求要**跨 90 天以上**的明细——超出 A 线门禁，转 B 线做汇总表。
- 结果与**已知的报表数对不上**——先别改 SQL 去凑数，先查是不是口径不同。
