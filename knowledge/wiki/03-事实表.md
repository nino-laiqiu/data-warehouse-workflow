# 03 事实表（10 张常用表）

每张表只写五件事：**粒度、主键、分区、上下游、坑**。字段细节以建表语句为准（`templates/ddl/`）。

## 关系总图

```
dwd_order_main_di ──1:N── dwd_order_item_di ──N:1── dim_product_df
        │                        │
        │ 1:1                    └──N:1── dim_shop_df
        ↓
dwd_pay_flow_di ──1:N── dwd_refund_di
        │
        └──────────┬──────────┬─────────────┐
                   ↓          ↓             ↓
        dws_trade_channel_1d  dws_trade_user_1d  dws_item_sale_1d
                   │          │             │
                   └──────────┴──────┬──────┘
                                     ↓
                          ads_trade_metric_1d / ads_trade_funnel_1d
```

## 1. `dwd_order_main_di` 订单主表

| 项 | 内容 |
|---|---|
| 粒度 | 一个订单一行 |
| 主键 | `order_id` |
| 分区 | `dt`，按 **`create_time`** 归日 |
| 更新 | 每日 `INSERT OVERWRITE` 分区；订单状态变化靠 T+1 回刷近 7 天分区 |
| 上游 | `ods_order_main_di` |
| 下游 | `dwd_order_item_di`、`dws_trade_channel_1d`、`dws_trade_user_1d` |

关键字段：`order_id`、`parent_order_id`（拆单前的父单）、`user_id`、`shop_id`、`channel_id`、`order_status`、`order_amt`（应付）、`pay_amt`（实付）、`freight_amt`、`discount_amt`、`create_time`、`pay_time`、`cancel_time`。

坑：
- **拆单**：一个父单拆成多个子单，`order_id` 各不相同。按订单数统计时先确认要不要合并父单，否则大促期间订单数虚高。
- **取消订单仍在下单表**：`order_status='cancelled'` 的行是真实发生过的下单行为，统计"下单量"要留、统计"有效订单"要滤。别用 `is_valid=1` 糊弄，那等于不区分。
- **`order_amt` ≠ `pay_amt`**：前者含运费和优惠前金额，后者是实付。GMV 用 `pay_amt`。

## 2. `dwd_order_item_di` 订单明细表

| 项 | 内容 |
|---|---|
| 粒度 | 一个订单行（一次下单里的一个 SKU） |
| 主键 | `order_id` + `item_seq` |
| 分区 | `dt`，跟主表一致 |
| 上游 | `ods_order_item_di` + `dwd_order_main_di` |
| 下游 | `dws_item_sale_1d`、`dws_trade_channel_1d` |

关键字段：`order_id`、`item_seq`、`sku_id`、`item_id`、`shop_id`、`category_id`、`qty`、`item_price`、`item_amt`、`discount_amt`。

坑：
- **同一 SKU 可以出现多行**（不同促销、不同仓库），所以主键是 `item_seq` 不是 `sku_id`。
- **赠品行 `item_amt=0` 但 `qty>0`**：算件数会把它算进去，算金额不会。要区分"销量"和"销售件数"。
- **优惠分摊**：`item_amt` 是分摊后的金额，`SUM(item_amt)` 应等于 `order_amt - freight_amt`，不等就是分摊逻辑有 bug，这是很好的日检项。

## 3. `dwd_pay_flow_di` 支付流水表

| 项 | 内容 |
|---|---|
| 粒度 | 一笔支付流水（一个订单可以有多笔：定金、尾款、部分支付） |
| 主键 | `order_id` + `pay_seq` |
| 分区 | `dt`，按 **`pay_time`** 归日 |
| 上游 | `ods_pay_flow_di` |
| 下游 | `dws_trade_channel_1d`、`ads_trade_metric_1d` |

关键字段：`pay_id`、`order_id`、`pay_seq`、`user_id`、`pay_amt`、`pay_channel`（微信/支付宝/银联）、`pay_status`、`pay_time`、`trade_no`（渠道流水号）。

坑：
- **重复回调**：渠道会重发通知，同一笔流水落多条。必须按 `(order_id, pay_seq)` 去重，`COUNT(1)` 会把 GMV 算高。
- **部分支付**：一个订单多笔流水，`SUM(pay_amt)` 要按 `order_id` 汇总后再判断是否结清。
- **退款不改变 `pay_status`**：退款是另一张表的事，不要在这里用状态字段表达。

## 4. `dwd_refund_di` 退款明细表

| 项 | 内容 |
|---|---|
| 粒度 | 一个退款单一行 |
| 主键 | `refund_id` |
| 分区 | `dt`，按 **`refund_time`**（退款成功时间）归日 |
| 上游 | `ods_refund_di` + `dwd_pay_flow_di` |
| 下游 | `ads_trade_metric_1d`、`dws_trade_channel_1d` |

关键字段：`refund_id`、`order_id`、`pay_id`、`user_id`、`refund_amt`、`refund_type`（退货退款/仅退款）、`refund_status`、`refund_time`。

坑：
- **跨期退款**：3 月的订单、4 月才退款，退款率按退款日归集时，4 月某天的退款率可能 >100%。这是对的，不是脏数据。
- **部分退款多笔**：一个订单可以退多次，`SUM(refund_amt)` 可能超过单笔支付。
- **退款状态有中间态**（申请中/审核中/成功/失败），只有 `refund_status='success'` 才计金额。

## 5. `dwd_user_behavior_di` 用户行为表

| 项 | 内容 |
|---|---|
| 粒度 | 一个行为事件一行 |
| 主键 | `event_id` |
| 分区 | `dt`，按 `event_time` 归日 |
| 上游 | `ods_behavior_log_di`（埋点日志） |
| 下游 | `ads_trade_funnel_1d`、`dws_trade_user_1d` |

关键字段：`event_id`、`user_id`（未登录为 `0`）、`device_id`、`session_id`、`event_type`（`pv`/`cart`/`fav`/`share`）、`page_id`、`item_id`、`channel_id`、`event_time`。

坑：
- **埋点重复上报**：弱网下客户端重试，同一 `event_id` 落多条，先去重。
- **`event_time` 与上报时间不同**：跨天补报会让昨天数据今天才到，所以这张表要允许 T+1 回刷。
- **未登录用户 `user_id=0`**：算 UV 时 `COUNT(DISTINCT user_id)` 会把所有游客算成一个人。要么用 `device_id`，要么明确"登录 UV"。

## 6. `dws_trade_channel_1d` 渠道日汇总

| 项 | 内容 |
|---|---|
| 粒度 | 天 × 渠道 |
| 主键 | `dt` + `channel_id` |
| 分区 | `dt` |
| 上游 | `dwd_order_main_di`、`dwd_pay_flow_di`、`dwd_refund_di` |
| 下游 | `ads_trade_metric_1d`、渠道日报 |

关键字段：`dt`、`channel_id`、`order_cnt`、`pay_order_cnt`、`gmv`、`pay_qty`、`pay_user_cnt`、`refund_amt`。

坑：
- **分子分母来自不同表**：`order_cnt` 来自订单表、`pay_order_cnt` 来自支付表，两边渠道缺失值处理不一致时，转化率会 >100%。
- **未识别渠道归 `other`**，不要丢行，否则总数对不上。

## 7. `dws_trade_user_1d` 用户日汇总

| 项 | 内容 |
|---|---|
| 粒度 | 天 × 用户 |
| 主键 | `dt` + `user_id` |
| 分区 | `dt` |
| 上游 | `dwd_order_main_di`、`dwd_pay_flow_di`、`dwd_refund_di` |
| 下游 | 复购/留存分析、`ads_trade_metric_1d` |

关键字段：`dt`、`user_id`、`order_cnt`、`pay_cnt`、`gmv`、`refund_amt`、`is_new_user`、`first_pay_time`。

坑：
- **`is_new_user` 依赖首次支付时间**：新用户定义一旦变化，历史分区必须整体回刷，否则同一天两种口径并存。
- 一个用户一天多笔支付，`gmv` 是多笔之和，`pay_cnt` 是笔数不是订单数。

## 8. `dws_item_sale_1d` 商品日销量

| 项 | 内容 |
|---|---|
| 粒度 | 天 × SKU |
| 主键 | `dt` + `sku_id` |
| 分区 | `dt` |
| 上游 | `dwd_order_item_di`、`dwd_pay_flow_di`、`dwd_refund_di` |
| 下游 | 商品榜单、动销率、`ads_trade_metric_1d` |

关键字段：`dt`、`sku_id`、`sale_qty`、`sale_amt`、`order_cnt`、`refund_qty`、`is_on_sale`（当日是否在架）。

坑：
- **动销率分母**：必须是"当日可售 SKU 数"，不是"历史所有 SKU 数"，更不是"有销量的 SKU 数"。
- **SKU 换绑类目**：商品改类目后，历史销量会跟着变。要么冻结 `category_id` 快照，要么接受回溯变化并写进文档。

## 9. `ads_trade_metric_1d` 交易指标宽表

| 项 | 内容 |
|---|---|
| 粒度 | 天 × 渠道 × 店铺（全站汇总行为 `channel_id='ALL'`、`shop_id='ALL'`） |
| 主键 | `dt` + `channel_id` + `shop_id` |
| 分区 | `dt` |
| 上游 | 三张 `dws_*_1d` |
| 下游 | 报表、看板、取数 |

关键字段：`dt`、`channel_id`、`shop_id`、`gmv`、`order_cnt`、`pay_user_cnt`、`aov`、`refund_rate`、`gmv_yoy`、`gmv_mom`。

坑：
- **`aov` / `refund_rate` 是冗余列**，只对"这一行"成立。跨店铺汇总时必须用 `SUM(gmv)/SUM(order_cnt)` 重算，不能 `AVG(aov)`。
- **`ALL` 行不能和明细行相加**，否则重复计算。
- 同比/环比是基于 `dt` 的窗口值，跨分区对比时注意历史分区是否被回刷过。

## 10. `ads_trade_funnel_1d` 交易漏斗

| 项 | 内容 |
|---|---|
| 粒度 | 天 × 渠道 |
| 主键 | `dt` + `channel_id` |
| 分区 | `dt` |
| 上游 | `dwd_user_behavior_di`、`dwd_order_main_di`、`dwd_pay_flow_di` |
| 下游 | 转化分析、增长看板 |

关键字段：`dt`、`channel_id`、`visit_uv`、`cart_uv`、`order_uv`、`pay_uv`，以及各级转化率。

坑：
- **漏斗要"同人同窗口"**：访问过、加购过、下过单、付过款的**同一批用户**。各步独立 `COUNT(DISTINCT user_id)` 再相除，会得到"各步人数比例"，不是漏斗。
- **窗口长度要固定**：当日访问、7 日内下单，这种跨天窗口必须写清楚，否则每天的数不可比。
