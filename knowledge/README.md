# knowledge/ —— LLM 知识库（记忆的"方法"部分）

回答一个问题：**这东西该怎么写**。

不回答：这个指标口径是什么（那是 `ontology/` 的事）。

## 五层

| 目录 | 放什么 | 例子 |
|---|---|---|
| `01_规范/` | 命名、分层、分区、注释等硬规范 | "DWD 表必须带 `dt` 分区；表名 `<层>_<域>_<实体>_<粒度>" |
| `02_方言/` | Hive / Spark SQL 的语法差异与性能陷阱 | "`ROW_NUMBER()` 去重会产生 shuffle，先按 key 分区再取数" |
| `03_范例/` | 可复用的 SQL 模板 | 漏斗聚合、比值重聚合、同环比 |
| `04_踩坑/` | 线上事故与排查结论 | "厂商回调重复推送导致到达量虚高，需按 `(msg_id, event)` 去重" |
| `05_历史/` | 历史需求与复用关系 | "同类需求出现过 3 次，可沉淀为指标" |

## 写作规则

1. **一条 chunk 只讲一件事**，标题即结论，正文给反例。
2. **必须可验证**：能写成 DQ 规则的，就往 `04_踩坑/` 里连规则一起写。
3. **不写口径**。发现口径类内容，转成 `ontology_delta` 提案交给本体管理员。
4. **标注适用版本**：Hive 2 vs 3、Spark 2.4 vs 3.x 行为不同的必须写明。

## 索引

`index/chunks.jsonl` 是检索用的元数据，每行一条：

```json
{"id":"k-0012","path":"04_踩坑/push-dup-callback.md","title":"厂商回调重复","tags":["push","dedup"],"verified_by":"DQ-PUSH-003"}
```

检索时先按 `tags` 粗筛，再由 LLM 读原文——不要把所有知识库塞进上下文，那是把知识库当缓存用。
