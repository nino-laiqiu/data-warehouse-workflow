# track-1 设计说明 · 宽表方案

## 方案

一张 `dws_user_profile_df`，一用户一行，12 个标签各占一列，`dt` 分区存每天全量快照。

## 为什么是宽表

- 下游是**运营圈人**：典型查询是 `WHERE basic_age_band = '25-34' AND purchase_order_cnt_30d IN ('2-3','4-9')`。宽表下就是一次分区扫描 + AND 过滤。
- 标签数已知且稳定（12 个，一年内预计不超 30 个），列宽可控。
- 单用户一行，便于直接和 `dim_user_df`、CRM 名单做 user_id join。

## 关键实现选择

| 选择 | 理由 |
|---|---|
| 全量快照而非增量 | 标签值会"变小"（近 30 天窗口滚动），增量合并需要回撤逻辑，代价高于全量重算 |
| `INSERT OVERWRITE` 指定分区 | 重跑幂等，天然可回刷 |
| 时间窗 `[dt-N, dt-1]` | 不含当天，否则同一分区重算结果会漂移（当天支付还在流入） |
| SCD2 维表先 `ROW_NUMBER` 取当前版本 | 不做这一步，用户会被多条历史版本放大成多行 |
| 缺失落 `UNKNOWN` 而非 NULL | NULL 会让 `WHERE tag = '男'` 静默漏人，且违反验收标准第 3 条 |
| 用户范围取维表全量 | 必须包含从未下单的用户，否则"未购"这类标签没有承载对象 |

## 分区与键

- 分区：`dt`（STRING，`yyyy-MM-dd`）
- 逻辑主键：`user_id`
- 存储：ORC + SNAPPY

## 风险

1. `pay_all` 取全历史（首单时间需要），分区裁剪只能到 `dt <= dt-1`，历史越长越贵——后续可换成"用户首单宽表"。
2. 偏好品类需要 `dwd_order_item_di` × `dim_product_df`，是整条链路最重的一段，90 天窗口约占总耗时 60%。
3. 加标签必须 `ALTER TABLE ADD COLUMNS` 并回刷历史，这是本方案最大的长期成本。
