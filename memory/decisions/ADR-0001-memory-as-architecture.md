# ADR-0001：为什么"记忆"要独立于"知识库"

- 状态：已接受
- 日期：2026-11-22

## 背景

设计文档里的四支柱是 skills / agents / 知识库 / 本体。落地时发现还缺一层：
**我们做过的决定**没有地方放。

知识库存的是"怎么写"（Hive 怎么去重、有哪些坑），本体存的是"是什么"（口径、实体）。
但"2026-11 我们决定 GMV 按支付时间归日、而不是按订单创建时间"这件事，两边都不合适：
放进知识库，它会和规范混在一起，没人知道它是规则还是历史；放进代码注释，等于没写。

## 决定

新增 `memory/` 目录，存决策、裁决、评审结论、教训四类，与 `knowledge/` 平级。

分界线：

| | 问题 | 稳定性 | 谁改 |
|---|---|---|---|
| `knowledge/` | 怎么做 | 相对稳定，随技术演进 | 任何有权限的人，走 PR |
| `memory/` | 为什么这么做 | **只增不改**，改动靠新 ADR 覆盖旧 ADR | 只能新增，不能删旧记录 |
| `ontology/` | 是什么 | 最严格，唯一事实源 | 只有 ontology-admin |

`runs/` 是短期记忆（一次运行的细节），`memory/` 是长期记忆（跨运行沉淀）。
两者不混：run 可以删，memory 不能。

## 后果

- 好处：口径争议有据可查，新人能顺着 ADR 看到决策链条，而不是只看最终代码。
- 代价：多一层维护成本。缓解方式是 ADR 极短（一页），不写综述。
- 风险：如果有人把定期报表结论塞进 memory，会退化成垃圾场。约束：只收决策与裁决，不收数据结论。
