# ADR-0003：角色编制收敛到 5 个

- 日期：2026-11-28
- 状态：已采纳（用户 m02353：「目前应该一共需要五个智能体 需求分析员 开发者1 开发者2 监督者 追踪者」）
- 取代：ADR-0001 之后逐轮加出来的 11 角色矩阵（orchestrator / ontology-admin / quality-officer / lineage-steward / doc-writer / analyst-writer 全部取消独立编制）

## 背景

前几轮为了让每个 stage 都"有人负责"，把流程拆成了 11 个角色。结果是：

- 6 个角色从来没有独立文件、也没有独立提示词，只存在于 `agents/README.md` 的一行矩阵里——写了但不存在；
- `orchestrator` 从第一天起就没跑过，一直是人对着文档执行；
- 每多一个角色就多一次交接，而交接本身不产生信息，只产生"我以为他会做"。

## 决定

编制固定 5 个：**需求分析员、开发者 1、开发者 2、监督者、追踪者**。

职责重新分配（不是删职责，是合并到最合适的那个角色）：

| 原角色 | 原职责 | 现在归谁 | 为什么是它 |
|---|---|---|---|
| `orchestrator` | 派活、验门、记账 | 派活 → 人/主线 agent；验门 → 脚本；记账 → 追踪者 | 派活是人的判断；验门已经全部脚本化（14 个校验器） |
| `requirement-translator` | P1 翻译 | 保留，并接管 P0 登记、P4 质量规则、A5 结论生成 | 登记是翻译的入口，DQ 规则是验收标准的可执行化，都在"定义侧" |
| `developer-1` | P2 双轨之一 | 保留，并接管 P5 血缘调度 | 裁决后隔离解除，实现者落地自己的调度最省事 |
| `developer-2` | P2 双轨之一 | 保留，P3 后退出 | 让它参与落地，等于破坏"两轨独立"的初衷 |
| `supervisor` | P3 比对裁决 | 保留（只选不写） | 让它写，它评的就是自己 |
| `chronicler` | 全程记录 | 保留，并接管 P6 交付文档 | 数据字典/上线单本来就是"记录"的产物，素材全在它的 journal 里 |
| `ontology-admin` | 写 `ontology/` | **取消**——只有人能改本体 | 让 agent 改事实源，等于把"口径唯一"交给一个会幻觉的东西 |
| `quality-officer` / `lineage-steward` / `doc-writer` / `analyst-writer` | P4 / P5 / P6 / A 线 | 见上表 | 职责是延伸，不是新工种 |

## 代价

1. 需求分析员一次要背 4 个 stage（P0/P1/P4/A5），提示词变长；用 `tools/role_prompt.py` 按 stage 生成，不让它一口气看到全部。
2. 开发者 1 在 P5 既写 SQL 又写调度，"自己给自己收尾"——这里确实没有第二双眼睛，靠 G5 的 `check_lineage.py` 兜底（成环/孤立/回滚步骤），不靠角色互评。
3. 取消 `ontology-admin` 后，本体变更必须有人工介入：`ontology_delta` 提案 → 人评审 → 人手改 YAML。这是**故意**的减速带。

## 什么情况下加回角色

出现下列情况之一，才值得重新讨论编制（否则一律 5 个）：

- 质量规则超过 50 条、且需要独立的规则维护节奏（那时 `quality-officer` 有独立工作量）；
- 血缘节点超过 50 个、调度任务超过 20 个（`lineage-steward` 才不是兼职）；
- 出现外部合规审计，交付文档需要独立签署（`doc-writer` + 审计留痕）。

## 检查

`tools/check_agents.py` 把这条决定写成了硬检查：角色数不等于 5 直接 FAIL。改编制必须先改这个 ADR，再改检查——防止下次又悄悄地加角色。
