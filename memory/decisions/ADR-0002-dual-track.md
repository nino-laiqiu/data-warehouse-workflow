# ADR-0002：B 线用双轨制开发 + 监督比对

- 状态：accepted
- 日期：2026-11-22
- 相关：[ADR-0001](ADR-0001-memory-as-architecture.md)、`flow/pipeline.yaml`、`agents/developer.md`、`agents/supervisor.md`

## 背景

一条需求一个人写，写完自己检查，然后把 SQL 交给下游。问题不在于"写错语法"——那个 `sk-sql-guard` 能拦。问题在于：

1. **口径理解偏差没人对照**。"按支付时间归日"这句话，一个开发者理解成 `pay_time` 的日期，另一个理解成支付流水落库时间。两份 SQL 都能跑，数字差 3%，谁也不知道谁对。
2. **自检没有约束力**。自己写的东西，自检会不自觉地只看自己关心的那几条规则。
3. **返工发生在最贵的时刻**。口径错了，往往要等表建好、刷完数、业务方看报表发现数不对，才被发现。

## 备选方案

| 方案 | 代价 | 为什么没选 |
|---|---|---|
| 单轨 + 自检 | 低 | 自检无法发现"自己没意识到的理解偏差"，而这正是主要风险 |
| 单轨 + 人工评审 | 中 | 评审者没有对照物，只能凭感觉看 SQL；且评审会流于形式 |
| 三人评审组 | 高 | 三个人仍然看同一份产出，缺少独立假设 |
| **双轨 + 监督比对** | 成本 ×2 | 选它 |

## 决策

同一份翻译稿，两个开发者**独立实现、互不可见**，再由监督者比对裁决。

关键设计：

- **隔离是硬约束，不是建议**。互相看得见，第二个人就只会做校对，产出趋同，比对失去信息量。`G2` 会扫 journal，发现跨轨读取直接作废该轮。
- **监督者不写新脚本**。它做选择与最小修补，逐条记录改动。整篇重写等于多了一个开发者，双轨白做。
- **口径冲突必须退回 P1**。监督者没有口径裁决权——有的话，双轨就变成"第三个开发者说了算"。
- **差异本身是资产**。两个人分歧的地方，往往就是需求写得含糊的地方。这些差异回流到 P1 的"待确认项"，下一条需求会写得更清楚。

## 代价（写清楚，免得三个月后后悔）

1. **成本翻倍**。同样的需求要写两遍。所以只对"建表 + 指标口径"这类一次做错、长期返工的事用双轨；A 线取数不用。
2. **趋同风险**。两个 LLM 开发者如果拿到相同的强 prompt，可能给出几乎相同的 SQL——`G2` 的 hash 相同检查就是为了抓这个。
3. **隔离需要工具保障**。靠 agent"自觉不看"是不可靠的，`must_not_read` 必须由运行时强制，否则这条规则迟早被绕过。

## 怎么判断这个决策对不对

上线三个月后回看两个数：

- **有效差异率**：两轨之间"语义"类差异的占比。太低（趋同）说明隔离没生效；太高说明翻译稿质量不够，问题在 P1 而不在 P2。
- **返工率**：G3 之后到上线之间，因口径问题退回 P1 的次数。这个数应该接近 0。

如果有效差异率长期低于 5%，说明双轨没产生独立假设，应该停掉，别硬撑。
