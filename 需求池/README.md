# 需求池 · 原始需求投放处

这里是"别人随手丢过来的需求"的落地处——邮件导出、群聊记录、会议纪要、Excel 清单、Word 文档，什么格式都行。
**不做整理，只做收集**：一旦放进这里，就不要改它（要改请另存新文件）。

> 目录名为什么叫"需求池"而不是"inbox"：因为投递的人不看英文。中文目录名在 git 与 Windows 上都正常。

## 谁会来看

| 谁 | 什么时候 | 做什么 |
|---|---|---|
| 需求雷达 `tools/scan_requirements.py` | 每天一次 / 手动 | 按 sha256 比对，发现**新增或改过**的文档，写 `_待确认.md` |
| 人（需求负责人） | 收到提醒后 | 判断"这个要不要做"，不做就在 `_待确认.md` 里划掉并说明 |
| 需求翻译者（P1） | 确认要做之后 | 建需求目录、登记、翻译成 8 段规格 |

## 怎么确认要开发

确认 = 一条命令把它接进流程（不是在这里改文件）：

```
# 1) 建需求目录（名字带日期，路径里只出现一次需求名）
requirements/复购率看板需求20261129/反馈者/

# 2) 把原件搬进去（原件不改内容），然后登记
python skills/sk-req-register/register.py --path "requirements/复购率看板需求20261129/反馈者/复购率看板-初稿.md" --proposer 增长组-张三 --channel 邮件 --submitted-at 2026-11-29
```

登记成功后会拿到 `REQ-YYYYMMDD-NN` 编号与 sha256，之后原件被改动会被 G0 校验抓到。

## 规则

1. **只增不改**：原始文档是证据，落进来就冻结；要修订另存 `-v2`。
2. **不要在这里做分类目录**：分类是整理，整理会带来"这条需求归哪类"的争论；需要时按文件名前缀（`growth-`、`supply-`）区分即可。
3. **`_` 开头的文件与目录雷达会跳过**：`_待确认.md`、`_scan_state.json` 都是雷达自己维护的，不要手改。
4. **敏感内容不要放**：这里是仓库的一部分（会被推送到 GitHub）。带个人信息、密钥、内部价格的文档先脱敏。

## 相关文件

- `_scan_state.json`：每个文件的 sha256 与首次发现时间，删掉等于"重新开始提醒"。
- `_待确认.md`：当前待人类确认的清单（勾选式），由雷达自动生成，可手写批注。

命令与原理见 [docs/核心能力与自动化.md](../docs/核心能力与自动化.md) 的 C3。
